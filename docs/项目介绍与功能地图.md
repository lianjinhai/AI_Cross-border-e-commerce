## 1. 项目定位与架构总览

### 1.1 项目定位

AI-电商ERP 是一个 **AI 原生跨境电商智能运营平台**（基于《需求分析与详细设计说明书 V8.0》演进）。以存量领域能力实现 + 总调度、大模型/规则双模与 RAG 知识库支撑业务闭环，正按冻结的 8 个领域能力契约迁移；不按员工角色建模，也不以聊天回复代替业务执行——

```
市场发现 → AI选品 → 供应商分析 → 利润计算 → 合规检测 → Listing生成
→ 一键铺货 → 广告增长 → 动态定价 → 订单处理 → 客服服务 → 售后逆向 → 经营分析
```

三大差异化能力（README.md:9-35、docs/DECISIONS.md:27-41）：

- **LLM/规则双模**：每个 Agent 方法统一走 `ask_json()`，配置了 API Key 走 LLM，任何失败无缝降级确定性规则引擎（`backend/app/agents/base.py:32-52`）。离线零配置可完整运行，接入大模型后同一套代码自动升级。
- **合规门禁（防封店）**：Listing 发布前三道关——平台规则包强制校验 → 平台必填字段校验 → 类目映射校验，任一不通过拒绝发布（`backend/app/services/adapters/base.py:73-100`）。
- **多租户 SaaS**：全部业务表带 `tenant_id` 查询强制过滤；superadmin 平台控制台与租户业务菜单完全隔离；代客访问带审计。

### 1.3 分层架构

单体模块化持续演进。AI 读取经 Tool，已迁移的写入由调度层提交提案，执行器落库；
定价只保存分析产物，不修改售价。尚未迁移的领域写入与 Base 审计仍是债务，
不得把下方已接管路径描述为全仓完成状态。当前仍是同步调度，Task/Session/Trace 后续迁移。

```
HTTP 路由 / Workflow Step
  → Workspace 身份和权限 → Orchestrator → 领域 Agent
      ├─ 读取：Tool → Service → models.py
      ├─ 动作提案：服务端 Policy / Permission / Risk / Approval
      │              → Action Executor → Business Service → 业务记录 + outcome
      └─ 定价分析：pricing_outputs → PricingRecord（不创建 Action）

发布：提交 → 等待人工批准 → 单独执行 → 人工 resume 工作流
边界：无上下文不得执行；原请求人与当前执行人权限均复核
```

### 2.13 数据流实例：`auto_listing` 自动铺货工作流

模板定义以 `backend/app/seed.py` 的 auto_listing 与实际租户模板为准。
引擎 `backend/app/workflows/engine.py` 使用服务端 run/step 范围和可信发起人，
持久化步骤输出，按 business_status 暂停门禁步骤及下游：

```
discovery/pick_candidates → product_ids
  → product/standardize_batch → 标准化商品范围、重复项
  → factory_opportunity/scan_private_supply_batch → 私域机会/收益门禁
  → supplier/match_best_batch → offers
  → compliance/check_batch → risk_high
  → listing/generate_batch → listing_ids
  → listing_review/review_batch → 上架复核
  → listing/publish_batch → pending_action_ids / published_product_ids
      （暂停：人工批准 → 单独 execute → 人工 resume）
  → ads/draft_batch → 本地广告草稿 campaign_ids，不启动投放
```

每步输出存 `WorkflowStep.output`；失败、门禁阻断和未执行步骤是不同状态，
恢复不能跳过被拒绝/失败的原 Action。缺少可信发起人的旧定时流程应等待人工恢复，
不临时挑选系统管理员代跑。AI 助手可以引导入口，聊天回复不代替审批。

- **任何失败**（未配置 Key / HTTP 错误 / 输出不是合法 JSON / 缺关键字段）→ 无缝降级调用无参 `fallback()` 规则引擎；
- 每次调用（无论成败）写 `AiLog`（agent/action/mode/model/prompt/response/latency/ok，base.py:54-58），可在「AI 设置」页审计（`GET /api/ai/logs`，routers/ai.py:80-85）；
- 各 Agent 在拿到结果后还会做**结构校验**再决定是否降级（如 discovery.py:127-128 校验五个维度字段齐全、compliance.py:89-90 校验 issues 是列表且含 risk_level）——保证 LLM 输出不可信时业务永远有确定结果。

收益（DECISIONS.md D3）：演示环境零配置跑通全流程；生产接 Key 同一套代码升级为 AI 生成；LLM 故障不阻塞业务。代价：规则引擎需与 LLM 输出同构维护（字段契约固化在 CONTRACT.md §2）。

### 3.4 双模实战走读（同一方法的 LLM 与规则两条路径）

## 8. 已知边界与诚实声明

> 以下为本项目当前的**真实边界**，避免对实现程度产生误解。与 README 的协议真实性声明（README.md:136-139）一致。

### 8.1 真实接入（有 Key 即可用，代码按官方文档实现并附链接）

| 能力 | 真实性 | 依据 |
|---|---|---|
| URL 商品采集 | **真实**：静态 HTTP + Playwright 渲染对任意公网商品页生效；1688 有官方 API Key 时走正式接口 | scraper.py 三层管线；open_1688.py 按开放平台签名规范实现（sign 函数 open_1688.py:53-58 为纯函数，有专项测试 test_1688_api_sign_and_fallback） |
| 店铺 OAuth | **真实**：1688（auth.1688.com + oauth2/getToken POST）、Shopee（v2 HMAC-SHA256）、TikTok（auth.tiktok-shops.com token/get|refresh）授权链接/换 token/刷新均按官方文档实现；本地用「粘贴授权码」与公网回调等价 | `adapters/ali1688.py`、`adapters/shopee.py`、`adapters/tiktok.py` 各自实现 |
| 授权后拉单 | **真实**：Shopee `order/get_order_list`、TikTok `order/search`、1688 `alibaba.trade.getSellerOrderList`，归一化入库并标注 source=api | 各适配器 fetch_orders |
| Shopee 上架 | **协议真实**：图片预上传 media_space → product/add_item 两步实现；需真实授权+类目映射+公网图片才会走通 | `adapters/shopee.py:198-238` |
| LLM/Embedding | **真实**：任意 OpenAI 兼容接口；未配置则全链路规则引擎兜底 | ai/llm.py、ai/knowledge.py |

### 8.2 演示通道（明确标注 demo，不是假数据冒充真实）

- `POST /api/orders/sync` 与演示店铺拉单走 `mock_market.gen_order`（模拟数据，source=demo，orders.py:59-66、shops.py:159-164）；真实部署时替换为各平台 OpenAPI（README 路线图亦声明）。
- 「本地模拟发布」（Listings 发布对话框缺省项，source=local）：仅本地置 published 状态 + 生成 internal external_id，**不与任何平台交互**，但合规门禁同样生效（listings.py:119-125）。
- 演示店铺（seed.py:274-278 建了一个 is_demo 的 1688 店铺）与全部种子数据可用 `POST /api/shops/purge_demo_data` 一键清空（保留账号/店铺/设置）。
- 趋势扫描基于 `backend/app/services/trend_candidates.py` 的日种子内置池确定性生成，非真实市场数据源；通过Action刷新builtin，不覆盖csv/api真实输入。

### 8.3 规则包的快照性质

- `DEFAULT_RULE_PACKS`（platform_rules.py:22-84）是**基于各平台公开卖家规则人工整理的快照**，带版本日期（2026-09-19）与 source_url，**不是平台官方实时下发**。平台规则随时可能变更，商用前务必核实最新平台文档。
- 已预留持续更新机制：数据库规则包版本覆盖内置（get_active_rules 87-100）+ `ERP_RULES_URL` 远程规则源拉取（check_updates 159-189），需自行部署/订阅规则源才会生效。

### 8.4 其他工程边界

- **Amazon 未接**：能力清单全空（can_order_sync/can_publish/can_refresh=False），前端自动禁用，不做假实现（`adapters/planned.py:51` 起）；规则包/门禁逻辑已就绪。
- **TikTok 上架未接**：product/create 需预上传图片+资质类目，协议已备待接（`adapters/tiktok.py` 文件头注释），当前 can_publish=False。
- **RAG 为轻量实现**：向量检索直接调 OpenAI 兼容 /embeddings + 余弦相似度（向量缓存在 SQLite JSON 列），未用向量数据库；接口已抽象（`retrieve`），可平滑升级（README 路线图）。
- **图片合规模型**：为规则启发（空图/URL 含 watermark 关键词），未走多模态模型识别（compliance.py:40-47）。
- **单库单体**：SQLite 开箱即用，未引入 Redis/消息队列/K8s（规划 27-29、36 章为生产化路线）；调度器/工作流用进程内线程。
- **打款/物流为记录闭环**：退款真实打款由平台/支付渠道后台完成（refunds.py:151 注释）；发货 tracking_no 为系统生成单号（orders.py:193），未对接物流商面单。
- **密钥安全**：API Key 全链路脱敏展示（ shops.py:46、ai.py:41-46）；口令 PBKDF2+静态盐（auth.py:17-25，静态盐为 MVP 简化）；`ERP_JWT_SECRET` 生产必须修改；superadmin 密码仅经环境变量注入。
- **测试覆盖口径**：29 个端到端用例覆盖主干链路与关键分支，未追求全分支覆盖（CONTRACT.md §7 的既定策略）。

### 8.5 与 V8.0 规划书的差距（生产化路线，承接 README「路线图」一节）

| 规划章节 | 现状 | 差距/方向 |
