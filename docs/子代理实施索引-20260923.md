第九轮记录「21 处列级差异…明文超 ~120 会被截断」。本轮用**两条独立建库路径**实测复核：

## 第十六轮（2026-09-24）：G-3 工厂账号 Context 通道 —— Phase 1.8 阻塞项清除（D23）

**性质**：本轮的起点是用户阶段计划（Phase 1.0 → 1.8）的**最后一环**：

本轮打通它，并顺带挖出一个**真实的 fail-open 缺陷**。

### 一、G-3 打通：只放行读，不放行写

`app/auth.py` 原先只放行 `/api/factory-network/portal/*` 与 `/api/auth/me`，
`/api/me/*` 一律 403。现改为**精确白名单**（`_FACTORY_SCOPE_PATHS`）：

| 路径 | 放行 | 理由 |
|---|---|---|
| `/api/me/workspaces` | ✅ 新增 | 只读：让工厂身份可被前端解析 |
| `/api/me/workspace-context` | ✅ 新增 | 只读：Context 权威源 |
| `/api/me/workspaces/{id}/switch` | ❌ 刻意拒绝 | **写语义**；工厂活动 Workspace 由 `SupplierPortalMember` 唯一确定，无可切换项 |

**为什么不用前缀匹配**：`startswith("/api/me/")` 会把 `/switch` 一并放行。
回退法实测（改成前缀匹配）立刻被测试抓住。

### 二、顺带挖出的真实缺陷：门户绑定不校验 status（fail-open）

`build_factory_context()` 查 `SupplierPortalMember` 时**只按 user_id 过滤、
未校验 status**，而路由层 `_portal_scope` 一直带 `status == "active"`。
→ 绑定停用后门户 API 403，但 Context 仍宣称 `supply:read/supply:write`。

**为什么算缺陷而非小瑕疵**：
1. Context 是前端**权威**权限来源（legacy 仅兜底）→「界面按钮可点、实际 403」；
2. `require_permission()` 的**后端鉴权**也以 Context 为权威判定路径；
3. **MEMBERSHIP 路径一直带 `status='ACTIVE'`**，工厂路径是唯一漏检分支
   → 属实现疏漏，非有意设计。
