## 二、第一轮论证：产品视角（角色职责是否清晰）

### 质疑 1：6 种角色是否过多？会不会有职责重叠？

**逐个核对职责**（基于后端实际权限）：

| 角色 | 能做什么 | 不能做什么 | 职责是否清晰 |
|---|---|---|---|
| PLATFORM_ADMIN | 管租户/授权/代客访问/平台规则 | **不能直接操作业务数据**（需进入租户） | ✅ 清晰 |
| OWNER（admin） | 全部业务 + 用户管理 + 设置 | 不能管租户（平台事务） | ✅ 清晰 |
| OPERATOR | 业务读写（商品/订单/采购/售后…） | 不能管用户/设置/平台 | ✅ 清晰 |
| COMPLIANCE | 合规审批（仅 listings 2 端点）+ 看板/BI/Listing/合规 4 页 | 不能改商品/订单/定价 | ⚠️ **偏窄**：只能审批，不能主动发起检测 |
| READ_ONLY（viewer） | 全部只读 | 不能写 | ✅ 清晰 |
| FACTORY_COLLABORATOR | 仅工厂门户（维护本厂资料） | 其他全部 | ✅ 清晰 |

**发现（产品视角）**：COMPLIANCE 角色**缺"发起合规检测"的能力**——它的职责是合规，却只能审批别人提交的，不能主动对商品发起检测。这是职责定义不完整。

**修正 1**：COMPLIANCE 应可发起合规检测（`POST /compliance/check`），但仍不能修改商品/发布 Listing。即：**读全部 + 合规相关写**。

### 质疑 2：viewer 看到写按钮是否可接受？

**反例推演**：viewer 看到「删除商品」按钮 → 点击 → 403 报错。用户体验差，且**暴露了系统能力边界**（安全上不可接受——信息泄露）。

**修正 2**：按钮级权限必须实现（隐藏或禁用 + 提示）。这是 P2 的核心。

## 三、第二轮论证：安全视角（越权风险）

### 质疑 3：前端隐藏按钮 = 安全吗？

**明确否定**：前端隐藏只是**体验优化**，不是安全边界。真正的安全在后端 `require_*`。

**因此本轮工作的定位**：
- 前端按钮权限 = **体验与信息隔离**（不暴露能力、不产生无效点击）
- 后端权限 = **安全边界**（已有，且已有 `test_security.py` 权限矩阵守护）

**结论**：前端改动**不能替代**后端校验，也不应因前端改动而放松后端。

### 质疑 4：P1（require_write 注释与实现矛盾）是真漏洞吗？

**核查**：superadmin 调业务 API 会先被 `get_current_user` 拦截——`auth.py:125` 明确：
```python
if user.role == "superadmin":
    if not _is_platform_scope_path(request.url.path):
        raise HTTPException(403, "平台服务商身份无业务 Workspace，请先「进入租户」后代客操作")
```

所以 superadmin **根本到不了 `require_write`**（在 `get_current_user` 就被拦）。`require_write` 不含 superadmin 是**正确的**，只是**注释误导**。

**修正 3**：修注释（不是修实现）。这是文档一致性问题，不是漏洞。

### 质疑 5：COMPLIANCE 扩权（修正 1）是否引入越权风险？

**分析**：给 COMPLIANCE 加 `POST /compliance/check` 的权限——该端点只**生成检测报告**，不修改业务数据。

**结论**：风险可控（只读 + 生成报告）。但要确认：合规报告会不会影响 Listing 状态？查代码：`ComplianceAgent.check` 在 target 是 listing 时**会写 `Listing.risk_level`**。

**修正 4**：这是必要的副作用（风险等级本来就是合规产出），但要在文档中明确说明。且 `risk_level` 影响发布门禁——**合规员能间接影响发布**。这是合理的职责（合规本来就有否决权）。

## 四、第三轮论证：工程视角（可维护性）

### 质疑 6：15 个页面逐个加权限判断，会不会散落各处难以维护？

**方案对比**：

| 方案 | 优点 | 缺点 | 采用 |
|---|---|---|---|
| 每页自行 `v-if="canWrite()"` | 灵活 | 散落 22 处，口径易漂移 | ✗ |
| **集中定义「能力→角色」矩阵 + 页面引用** | 单一事实源，改一处生效 | 需先定义矩阵 | ✓ **采用** |
| 自定义指令 `v-permission="'product:write'"` | 声明式简洁 | 新增全局指令，需维护 | 可选（后续） |

**修正 5**：在 `permissions.js` 集中定义**页面级能力矩阵**（`can('product:write')` 形式），页面只引用，不自行判断角色。**单一事实源**。

### 质疑 7：如何避免"改前端漏改后端"的不一致？

**修正 6**：新增**权限一致性测试**——用同一份能力矩阵，同时校验：
1. 前端矩阵与后端 `require_*` 的角色集合一致（静态比对）
2. 每个页面的写操作都有对应按钮权限控制（覆盖率检查）

这样任何一侧漂移都会被测试抓住。

### 质疑 8：P5（_ROLES 重复定义）如何根治？

**修正 7**：角色常量收敛到单一模块（如 `app/roles.py`），`admin.py` 与 `routers/auth.py` 均从该模块导入。 <!-- docs-ok: 提案中的未来文件，尚未创建 -->

## 六、论证结论

| 轮次 | 关键结论 |
|---|---|
| 第一轮（产品） | 6 角色职责基本清晰；**COMPLIANCE 缺发起检测能力**（需补）；viewer 看到写按钮不可接受 |

| 第三轮（工程） | **集中能力矩阵**（单一事实源）替代散落判断；**新增一致性测试**防漂移；角色常量收敛 |

**核心判断**：用户说的"混在一起"准确指的是——**框架层已分流，但页面层（按钮/操作）未分流**，导致同一页面上不同角色看到相同的操作入口。这是真实的体验与信息隔离问题，需要系统性补齐。

## 七、独立复核（fresh eyes，实施前）

> 复核方式：不预设方案正确，专找"重复建设/遗漏事实源"。

### 复核发现 1（严重）：方案 F1「新增能力矩阵」是重复建设

**方案原设计**：在 `permissions.js` 新增页面级能力矩阵 `can(capability)`。

**实证反驳**（Read 两个文件）：
- **后端已有权威矩阵**：`app/services/workspace_context.py:72` 的 `ROLE_PERMISSIONS`
  ```python
  ROLE_PERMISSIONS = {
      ROLE_OWNER: _READ | _WRITE | {"workspace:member:admin", "compliance:approve"},
      ROLE_OPERATOR: _READ | _WRITE,
      ROLE_READ_ONLY: _READ,
      ROLE_COMPLIANCE: {"compliance:read", "compliance:approve", "listing:read", "product:read"},
      ROLE_PLATFORM_ADMIN: {"platform:admin"},
      ROLE_FACTORY_COLLABORATOR: {"supply:read", "supply:write"},
  }
  ```
  权限 key 命名规范已存在（`product:write`、`order:write`、`finance:write`、`purchase:write`、`settlement:write`、`refund:write`、`ai:write`、`compliance:approve`…）
- **前端已有查询接口**：`workspace.js:80` 的 `hasPermission(key)` → 读 Context 的 `permissions` 数组
- **`permissions.js:48` 已在用**：`canWrite()/canAdmin()/canApprove()` 都基于 `hasPermission`

**结论**：方案若新增前端矩阵，会造成**双事实源**（后端一套 key、前端又一套），必然漂移。**必须复用后端权限目录**。

### 修正 8（关键）：前端只做「能力 key → 按钮」的映射，不重新定义角色

```
后端 ROLE_PERMISSIONS（唯一事实源）
        ↓ GET /api/me/workspace-context 返回 permissions[]
前端 hasPermission('product:write')（已有）
        ↓
页面按钮 v-if="can('product:write')"（本轮新增，薄封装）
```

`permissions.js` 新增的 `can(key)` 只是 `hasPermission(key)` 的**带 legacy 兜底的薄封装**（与既有 `canWrite()` 同构），不新增任何角色-权限定义。

### 复核发现 2：COMPLIANCE 扩权需要补**权限 key**

**方案原设计**：COMPLIANCE 可发起合规检测（改后端装饰器）。

**实证**：COMPLIANCE 的权限集是 `{"compliance:read", "compliance:approve", "listing:read", "product:read"}`——**没有写权限**。而 `POST /compliance/check` 用 `require_write`。

**修正 9**：应新增权限 key `compliance:check`，并：
1. 加入 `ROLE_COMPLIANCE` 与 `ROLE_OWNER`（owner 本就有 write，加 key 只为语义清晰）
2. `POST /compliance/check` 改用 `require_permission("compliance:check")`
3. 前端按钮 `v-if="can('compliance:check')"`

这样**权限模型自洽**（不靠"给合规员开写权限"这种粗粒度做法）。

### 复核发现 3：15 个页面的按钮权限，需要先确认**每页对应哪个 key**

不能凭感觉映射。需逐页核对操作与 key 的对应（如「删除商品」→ `product:write`、「发布 Listing」→ `listing:write`、「结算付款」→ `settlement:write`）。

**修正 10**：实施前先产出**页面-操作-权限 key 对照表**（作为实施清单与验收依据），避免映射错误。

### 复核发现 4：工厂门户（FactoryPortal）的权限 key 是 `supply:read/write`

**实证**：`ROLE_FACTORY_COLLABORATOR: {"supply:read", "supply:write"}`。

**修正 11**：FactoryPortal 的写操作应受 `supply:write` 控制（而非笼统的 `canWrite()`，后者基于 `_WRITE_PERMISSIONS` 集合，不含 supply）。

### 修正后的定稿（更新 §5）

| # | 改动 | 修正后内容 |
|---|---|---|
| B1 | 修 `require_write` 注释 | 不变（注释与实现一致化） |
| **B2** | **新增 `compliance:check` 权限 key** + 加入 ROLE_COMPLIANCE | 替换原"改装饰器"方案 |
| B3 | 角色常量收敛 | 不变 |
| **F1** | `permissions.js` 新增 `can(key)` 薄封装（**复用 hasPermission，不新建矩阵**） | 替换原"新增能力矩阵" |
| **F2** | 15 个页面按**对照表**加按钮权限 | 需先产出对照表 |
| **F3** | **新增页面-操作-权限 key 对照表文档** | 新增项（实施依据） |

### 复核结论

原方案有 1 处**重复建设**（F1）与 1 处**粒度不当**（B2），均已修正。修正后方案**复用既有权威事实源**，符合"严谨且可维护"要求。

### 8.3 关键设计决策（论证产出）

| 决策 | 理由 |
|---|---|
| **不新建前端权限矩阵** | 后端 `ROLE_PERMISSIONS` 已是权威事实源，前端 `can()` 只做查询 + legacy 兜底（复核修正 8） |
