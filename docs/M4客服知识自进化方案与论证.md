## 一、问题定义（基于代码事实）

### 1.1 现状缺口

`app/agents/support.py::auto_reply()` 的现有行为（已 Read 确认）：

```python
def _template(self, intent, conv, text):
    ...
    if intent == "product_qa":
        docs = retrieve(self.db, self.tenant_id, text, top_k=2)  # 只读
        extra = f"相关说明：{docs[0]['content'][:120]}" if docs else ""
    ...
    return "感谢您的留言！已收到您的问题，客服小姐姐会尽快回复；..."  # 兜底：无信息量
```

**缺口**：意图为 `other` 或 `retrieve()` 返回空时，问题被兜底话术糊过去，**没有留下任何痕迹**。同一个问题被问 100 次，系统仍然不知道。

### 1.2 目标

让高频问题**沉淀为知识**，下次能命中检索——但要避免"AI 自己编答案污染知识库"。

## 二、方案初稿

新增 `KnowledgeCandidate` 表记录未命中问题，按 `hit_count` 累积；高频问题沉淀为知识。

**初稿流程**：
```
买家提问 → auto_reply → 检索未命中 → 记录候选(hit_count+1)
                                          ↓
                          高频(≥5次) → 自动入库 KnowledgeDoc
                          低频      → 人工审核后入库
```

## 三、第一轮论证：安全边界（最重要）

### 质疑 1：自动入库的**答案从哪来**？

候选表记录的只有**问题**（`question_text`），没有答案。若由 AI 生成答案草稿并自动入库：

**反例推演**：买家问"这个充电器能带上飞机吗？"，AI 生成"可以，符合航空标准"→ 自动入库 → 下次所有买家都收到这个回答 → **若实际不能带，造成误导甚至纠纷**。

**结论：AI 生成答案自动入库不可接受**。这是与"炫技式 AI"的分界线。

### 修正 1（关键设计）：只沉淀**人工验证过的答案**

候选记录时**同时捕获该会话后续的 operator 人工回复**作为 `answer_draft`：

```python
# 候选的答案来源优先级
answer_source = "operator"   # 客服人工回复过 → 可信，可自动入库
              | "none"       # 无人回复 → 永远只能人工处理，绝不自动入库
```

**这改变了能力性质**：不是"AI 自己学"，而是**"AI 辅助沉淀人工经验"**——把已经人工验证过的答案，在高频复现时自动固化为知识。安全性与实用性兼得。

### 质疑 2：自动入库应该默认开启吗？

**反例**：租户刚上线，客服回复质量不稳定，自动入库会固化低质量答案。

**修正 2：默认关闭，租户显式开启（opt-in）**

配置项 `Setting["knowledge_learning"] = {"auto_learn_enabled": false, "auto_learn_threshold": 5}`

理由：延续项目已有的"不擅自变更业务数据"原则（与 M3 巡检"只告警不执行"同源）。

### 质疑 3：自动入库的知识会污染 RAG 检索吗？

**风险**：错误答案被检索出来 → 客服回复错误 → 店铺声誉损失。

**修正 3**：三重标识，让污染可识别、可回退
1. `KnowledgeDoc.source = "auto_learned"`（复用已有字段，前端可筛选/标识）
2. `KnowledgeDoc.tags` 含 `auto_learned`（便于批量操作）
3. **一键撤销**：`DELETE /api/knowledge/candidates/{id}/revoke` 同时删除入库文档并标记候选为 `rejected`

## 四、第二轮论证：工程可维护性

### 质疑 4：`question_hash` 如何计算？相似问题会不会算成不同候选？

**方案对比**：

| 方案 | 优点 | 缺点 | 采用 |
|---|---|---|---|
| 原始文本 hash | 简单 | "什么时候发货" vs "什么时候能发货" 算两个 | ✗ |
| 归一化后 hash（去空格/标点/小写） | 简单且改善明显 | 仍无法处理同义改写 | ✓ **首版采用** |
| 语义聚类/向量相似度 | 效果好 | 引入向量库依赖、阈值调优、难以维护 | ✗ 过度工程 |

**修正 4：采用归一化 hash + 唯一约束**

```python
def question_hash(text: str) -> str:
    """归一化后哈希：去空白/标点、转小写，使格式差异不影响聚类。"""
    norm = re.sub(r"[\s\p{P}]+", "", (text or "").lower())
    return hashlib.sha256(norm.encode()).hexdigest()[:24]
```

数据库加 `UNIQUE(tenant_id, question_hash)` —— 与项目已有做法一致（`uq_orders_shop_external`）。

**论证理由**：候选只是"线索"，聚类不完美不影响正确性（最多是多一条候选）。引入向量聚类会让维护成本陡增，违背"可维护"要求。

### 质疑 5：候选表会不会无限增长？

**推演**：每次未命中都插一行 → 长期可能数万行。

**修正 5**：
- 归一化 hash 去重（同类问题只有一行）
- `last_seen_at` 字段支持按时间清理（**不自动删**，避免丢失线索）
- 端点支持按 `hit_count` 排序，低频噪音沉底

### 质疑 6：并发安全？

**风险**：两个 `auto_reply` 同时处理同一问题 → 重复插入候选。

**修正 6**：`UNIQUE(tenant_id, question_hash)` 约束 + 插入冲突时改为 `hit_count += 1`（乐观更新）。这与项目 `platform_rules` 的 upsert 模式一致。

### 质疑 7：记录候选失败会不会影响客服回复？

**风险**：候选写入异常导致 `auto_reply` 抛错 → 客服不可用。

**修正 7**：记录逻辑用 try/except 包裹，失败只记日志不抛错——**复用 `BaseAgent.record_decision` 的既有模式**（"审计不能阻塞业务"）。

## 六、定稿方案

### 6.1 数据模型

```python
class KnowledgeCandidate(Base):
    """客服知识候选（M4）：未命中问题沉淀，人工验证过的答案可自动固化。

    安全约束（红线）：answer_source == "none" 的候选永远不可自动入库，
    也不允许人工"采纳为知识"（无答案可采纳，只能先补答案）。
    """
    __tablename__ = "knowledge_candidates"
    id, tenant_id
    question_hash: str      # 归一化哈希，UNIQUE(tenant_id, question_hash)
    question_text: str      # 原始问题（首次出现时记录）
    intent: str             # 分类意图
    hit_count: int          # 出现次数
    answer_source: str      # operator(人工回复过) / none(无答案)
    answer_draft: str       # 人工回复内容（answer_source=operator 时）
    status: str             # pending / approved / rejected / auto_learned
    doc_id: int | None      # 采纳后关联的 KnowledgeDoc
    auto_learned: bool      # 是否由自动学习入库
    last_seen_at, created_at
```

### 6.2 配置（Setting 表）

```json
"knowledge_learning": {
  "auto_learn_enabled": false,     // 默认关闭（opt-in）
  "auto_learn_threshold": 5        // 高频阈值
}
```

### 6.3 流程

```
auto_reply → 检索未命中 → record_candidate()
                              ↓
              ┌───────────────┴───────────────┐
              ↓                               ↓
   answer_source=operator            answer_source=none
   (客服人工回复过)                   (无答案)
              ↓                               ↓
   若开启自动学习且 hit≥阈值          仅累积，等人工补答案
              ↓
   自动入库 KnowledgeDoc(source=auto_learned)
              ↓
   记录 AiDecision（可追溯）
```

### 6.4 端点（挂 `/api/knowledge`）

| 方法 | 路径 | 作用 |
|---|---|---|
| GET | `/candidates` | 候选列表（按 hit_count 排序，支持 status 筛选） |
| POST | `/candidates/{id}/answer` | 人工补写答案（answer_source → operator） |
| POST | `/candidates/{id}/approve` | 采纳为知识文档（需有答案） |
| POST | `/candidates/{id}/reject` | 拒绝候选 |
| POST | `/candidates/{id}/revoke` | **撤销自动入库**（删文档 + 标记 rejected） |
| GET/PUT | `/learning/settings` | 自动学习配置（开关 + 阈值） |

### 6.6 验收标准

1. 未命中问题被记录为候选，重复提问 `hit_count` 递增
2. **`answer_source=none` 的候选无法采纳**（安全红线）
3. 人工补答案后可采纳，知识库出现文档且能被检索到
4. **默认不自动入库**（`auto_learn_enabled=false`）
5. 开启后：高频 + 有答案 → 自动入库，`source="auto_learned"`
6. **撤销后文档被删除**，候选标记 rejected
7. 归一化 hash：格式不同但内容相同的问题归为同一候选
8. 记录失败不影响客服回复（容错）
9. 全量回归不破坏存量（197 → 197+新增）

| 论证轮次 | 关键修正 |
|---|---|
| 第一轮（安全边界） | ① 只沉淀人工验证过的答案（AI 不自己编答案）② 默认关闭自动学习 ③ 三重标识 + 一键撤销 |

## 八、独立复核（实施前，fresh eyes）

> 复核方式：不预设方案正确，专找时序/数据流漏洞。

### 复核发现 1（严重）：`answer_source` 捕获时序不成立

**方案原假设**：`auto_reply()` 被调用时，能从会话中读到 operator 的人工回复作为 `answer_draft`。

**实证反驳**（Read `app/routers/support.py:80-97`）：
- `auto_reply` 与 `reply` 是**两个独立的、由人手动触发的端点**
- operator 可能在 `auto_reply` **之前**回复（此时该走 reply 不触发候选）
- operator 也可能在 `auto_reply` **之后**才回复（此时 auto_reply 已执行完，读不到答案）
- 实测演示库：**0 个会话同时有 buyer + operator 消息**（`grep` + SQL 验证）

**结论**：按原方案，`answer_source` 将恒为 `none`，**自动学习永不生效**——方案有致命缺陷。

### 修正 8（关键）：候选记录与答案捕获**解耦**

```
时刻 T1: 买家提问 → auto_reply 检索未命中 → 只记录「问题」到候选 (answer_source=none)
时刻 T2: operator 人工回复（经 /reply 端点）
          ↓
         该端点增加一步：尝试把回复回填到「同会话未命中问题」的候选上
          ↓
         answer_source → operator, answer_draft = 人工回复内容
时刻 T3: 下次同类问题复现 → hit_count 递增 → 若开启自动学习且达标 → 入库
```

**实现要点**：
1. `reply` 端点（operator 回复）增加**回填逻辑**：查找同会话最近 N 条 buyer 消息对应的候选，把本次 operator 回复作为 `answer_draft`
2. 回填只在 `answer_source == "none"` 时执行（不覆盖已有人工答案）
3. 回填失败不影响回复（try/except 包裹）

**这个修正让方案从"不可用"变为"可用"**，且逻辑更符合真实业务流程（客服先答，系统后沉淀）。

### 复核发现 2：候选与消息的关联需要会话维度

原方案只有 `question_text`，无法把后续 operator 回复关联回来。

**修正 9**：候选增加 `conversation_id` 字段（记录首次出现的会话），回填时按会话查找。

### 复核发现 3：`_template` 中 `product_qa` 分支已用 retrieve

`support.py:60` 的 `product_qa` 分支已经调用 `retrieve()` 并把结果拼进回复。若在此分支也记录候选，会把"已有知识可参考"的情况误判为"未命中"。

**修正 10**：候选记录条件收紧为：
- 意图 == `other`（完全没分类）**或**
- `retrieve()` 返回**空列表**（真的没有任何相关知识）

不满足则不记录，避免噪音。

### 复核结论

| 发现 | 严重度 | 修正 |
|---|---|---|
| 答案捕获时序不成立（自动学习永不生效） | **严重** | 解耦：reply 端点回填答案 |
| 候选无法关联后续回复 | 中 | 增加 `conversation_id` |
| 候选记录条件过宽会产生噪音 | 低 | 收紧为 other 或 retrieve 为空 |

**修正后定稿**：方案可行，进入实施。
