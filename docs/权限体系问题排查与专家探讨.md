# 权限体系问题排查与专家探讨

> 触发：用户反馈「发现的问题，先找专家探讨一下，讨论出一个最佳方案，然后进行修复，最后再严格校验」
> 排查方式：主动排查（前端实测 + 代码审计 + 测试覆盖审计）

---

## 一、排查结果（主动发现的 4 个问题）

### P1【严重】新增的 `can()` 函数**无测试覆盖**

**证据**：
```bash
grep -c "can(" frontend/tests/permissions.test.js  # → 0（仅 canWrite/canAdmin/canApprove 被导入测试）
```
`permissions.test.js` 导入的是 `canAdmin, canApprove, canWrite, currentUser, defaultLanding, identityFrom, routeRedirect`——**不含 `can`**。

**影响**：本轮为 16 个页面新增的按钮权限全部依赖 `can(key)`，而它**没有任何测试守护**。一旦 `can()` 逻辑出错（如 legacy 兜底表漏 key），16 个页面的按钮会静默消失或错误显示。

### P2【严重】前端构建产物**可能被浏览器缓存**，导致权限修复未生效

**证据**：本轮多次遇到"改了源码、构建了、浏览器仍显示旧界面"（如 Knowledge 页 el-tabs 不出现、候选表格显示旧数据）。根因是 SPA 懒加载 chunk 被浏览器缓存。

**影响**：用户可能看到**旧的权限行为**（按钮该隐藏没隐藏），误以为修复失败。

### P3【中】`can()` 的 legacy 兜底表与后端权限目录**可能漂移**

**证据**：
- 后端权威：`workspace_context.ROLE_PERMISSIONS`（6 角色 × 完整 key）
- 前端兜底：`permissions.js` 的 `LEGACY_CAPABILITIES`（4 角色 × 手写 key 列表）

两者**手工维护、无一致性测试**。后端加 key 时前端可能漏加（如本轮新增 `compliance:check` 后，我手工补进了 `LEGACY_CAPABILITIES`，但**无测试保证未来同步**）。

### P4【中】`FactoryPortal.vue` 权限覆盖缺失（已在文档声明为遗留）

**证据**：`grep -c "can(" FactoryPortal.vue` → 0

**影响**：工厂伙伴页面的写操作无前端权限控制（后端有 `supply:write` 保护，但前端按钮无控制）。

## 二、专家探讨（三个视角）

### 视角 A：前端工程专家

**对 P1 的判断**：这是**最严重**的问题。理由：
- `can()` 是本轮所有页面权限的**唯一入口**（16 个页面 × 平均 2-3 个按钮 = 40+ 处引用）
- 单点故障：`can()` 错 → 全部页面权限错
- 且 `can()` 有**两条分支**（Context 路径 / legacy 兜底路径），两条都要测

**建议**：补 `can()` 的完整测试矩阵（6 角色 × 代表性 key × 两种 Context 状态）。

**对 P3 的判断**：前后端权限表手工同步**必然漂移**。但**不能**让前端去拉后端常量（前端运行时无法 import Python）。
**建议**：用**契约测试**——前端测试里硬编码期望（与后端 `ROLE_PERMISSIONS` 对齐），后端测试里断言前端测试文件包含相同 key。任一侧改了另一侧会红。

### 视角 B：安全专家

**对 P2 的判断**：缓存问题在**生产环境是灾难**——用户可能长期使用旧版前端（含旧权限逻辑），而后端已收紧，造成"前端能点、后端拒绝"的困惑，或更糟：前端旧版**放开了按钮**但后端已收紧（此时安全无碍，但体验差）。

**关键澄清**：P2 **不影响安全**（后端是安全边界），只影响体验与信任。必须说清楚，避免过度反应。

**建议**：
1. 构建产物文件名带 hash（Vite 已做）+ `index.html` 不缓存
2. 后端给 `index.html` 加 `Cache-Control: no-cache`，静态资源加长缓存（`max-age` + 文件名 hash 保证更新）
3. 这不是本轮引入的问题，但**放大了本轮的验证难度**

**对 P4 的判断**：工厂伙伴的权限边界**后端已守住**（`supply:write` + 路径门禁）。前端未控制是**体验问题**，非安全漏洞。优先级可低于 P1。

### 视角 C：测试策略专家

**对 P1/P3 的统一建议**：**分层测试**
| 层 | 测什么 | 谁守护 |
|---|---|---|
| 后端 | 角色→权限 key 映射（已有 `test_workspace_dual_read` 一致性 + 我新增的 `test_role_permissions`） | ✅ 已有 |
| 前端单元 | `can(key)` 的 Context 路径 + legacy 兜底路径 | ❌ **缺（P1）** |
| 前后端契约 | 前端 `LEGACY_CAPABILITIES` 与后端 `ROLE_PERMISSIONS` 一致 | ❌ **缺（P3）** |
| 端到端 | 6 角色实际渲染的按钮可见性 | ❌ 缺（浏览器实测可覆盖） |

**对"严格校验"的定义**：四层都要有，缺一层就有一类漂移无人发现。

## 三、方案对比与定稿

### P1 修复方案对比

| 方案 | 优点 | 缺点 | 采用 |
|---|---|---|---|
| 补 `can()` 单元测试 | 直接、快 | 不解决 P3 漂移 | ✓ **基础** |
| 加前端 E2E（Playwright） | 覆盖真实渲染 | 引入重依赖、慢 | ✗ 本轮不做 |
| **补单元测试 + 契约测试** | 覆盖 P1+P3 | 需设计契约断言 | ✓ **采用** |

### P3 修复方案对比

| 方案 | 优点 | 缺点 | 采用 |
|---|---|---|---|
| 前端运行时拉后端权限目录 | 单一事实源 | 前端仍需兜底表（工厂账号无 Context） | ✗ 不能消除兜底 |
| **契约测试双向断言** | 任一侧漂移即红 | 需维护两处期望 | ✓ **采用** |
| 代码生成（从后端导出前端常量） | 彻底消除手工同步 | 引入构建步骤、增加复杂度 | ✗ 过度工程 |

### P2 修复方案

| 措施 | 说明 |
|---|---|
| `index.html` 加 `Cache-Control: no-cache` | 确保入口永不用旧版 |
| 静态资源（带 hash）加长缓存 | 性能不受影响 |
| 前端请求加版本探测（可选） | 检测到新版本提示刷新 |

### P4 处理

| 措施 | 说明 |
|---|---|
| 补齐 FactoryPortal 按钮权限 | 用 `supply:write`；若当前无写按钮渲染分支，则在文档中明确标注"待页面结构稳定" |

## 五、专家探讨的额外发现（值得记录的判断）

1. **P2 不影响安全**：前端隐藏/显示按钮不是安全边界，后端 `require_*` 才是。缓存问题只影响体验与信任，不应被当作安全漏洞处理（避免过度反应）。
2. **`can()` 的双路径必须都测**：Context 路径（正常）与 legacy 兜底（工厂账号/网络失败）行为不同，只测一条会有盲区。
3. **契约测试优于代码生成**：代码生成看似"彻底"，但引入构建耦合与调试难度；契约测试用两处期望 + 双向断言，成本低且失败信息明确。
4. **P4 优先级最低**：后端已守住安全边界，前端是体验优化。

1. **P2（缓存）不影响安全**：前端隐藏按钮不是安全边界，后端 `require_*` 才是。缓存只影响体验与信任，避免被误当漏洞处理。
