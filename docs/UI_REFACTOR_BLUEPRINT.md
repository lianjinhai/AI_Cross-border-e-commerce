# 前端业务体验整改计划 R2

> 日期：2026-10-14。状态：实施建议，尚未执行；供产品、前端、后端、QA 分派使用。
> 用户反馈：8000 旧版、8001 V9 均混乱、不好用。目标是让已有后端能力变成可完成的业务任务，允许大幅调整前端。
> 本计划不宣告旧验收无效，也不沿用其“完成”作为本轮可用性结论。既有 V9 冻结文档继续作为历史与契约依据；涉及导航、组件契约的调整，实施时明确登记变更。

## 1. 结论与边界

以 frontend-v9 为唯一整改基底，不创建第三套前端。旧 frontend 用于功能对照和切换回退；验收前不删除。保留 Vue、Element Plus、现有身份体系、领域服务与 Agent OS。可重做页面布局、导航、交互、前端数据适配及组件组合。

整改先后顺序：纠正接口与功能断点 → 做通商品上线主旅程 → 重组工作台与导航 → 扩展履约和利润闭环 → 验证并切换。视觉规范从首批开始统一，但不能用换皮替代功能验收。

本次是源码与文档静态核对，没有登录浏览器、执行业务请求、修改数据库或验证在线端口。8000/8001 的使用体验来自用户反馈；部署历史来自既有记录。本计划中的布局问题属于设计判断，接口差异属于代码证据，运行结果需后续复现。

风险：现有工作区有他人未提交修改，包含 workbench、后端入口、旧 Dashboard、V9 配置与验收文档。接手前登记归属，禁止重置、覆盖或混入提交。本文仅新增计划并登记文档地图。

## 2. 当前问题：证据与影响

| ID | 已核对证据 | 对用户的影响 | 首批处理 |
|---|---|---|---|

| E11 | 既有进度称 UX-F/R1 完成，视觉验收仍列“待截图”；实现计划主要依赖纯函数测试 | 通过构建/单测不等于页面操作可用 | 增加真实组件交互与浏览器业务验收，不以页面数结项 |

上述问题是重点抽查，不是全站零遗漏审计。首阶段必须拓展到所有可见菜单及所有写操作。

## 3. 后端能力如何变成前端价值

能力分级：A=源码已见端点/模型；B=前端已接但仍需联调验收；C=未核实或仍有后端缺口。A/B 均不代表真实外部平台接通。

| 领域 | 已有依据/可复用资产 | 前端应呈现的价值 | 补核重点 |
|---|---|---|---|
| Workspace/权限 | 现有 Context、Store Scope、权限模块、三空间外壳 | 当前空间/店铺始终明确；只显示可用操作 | 切换清缓存、撤权、只读、合规/工厂/平台隔离 |
| 商品与供给 | products 域及商品、供应商、货源匹配页面 | 商品准备度、货源选择、成本依据和缺口 | 字段、关联 ID、导入/采集及批量能力逐个对照 |
| Launch（A/B） | launch 路由已有 context、创建、列表、详情、steps、actions、sync、events | 当前阶段、阻断、负责人、合法下一动作、执行结果 | 每种 action 的真实 handler/能力边界；不能沿用旧清单说“无 API” |
| 渠道聚合（A/B） | channels_dto 按店铺聚合活跃实例及历史 | 一个商品多店独立进度，直接继续某店流程 | E01；审批、外部状态和主档状态分开 |
| 素材（A/B） | 素材版本、权利与核验 API | 哪张素材能在哪个市场用于发布，以及原因 | E02—E05；上传托管/文件内容核验仍需单独确认 |
| 发布与审批 | Listing、Action、发布回执及既有组件 | 清楚区分待审、批准、执行、提交和核验在售 | 单店目标、审批过期、权限与版本变更、重试 |
| 待办工作台（WIP） | 工作区已有 workbench 路由和服务，尚未提交 | 合并跨域待办，直达具体对象和动作 | 合入状态、sources/partial、分页、总数与去重 |
| 定价/财务/广告 | 已有独立 API 域与对应页面 | 由利润变化追溯到成本、费用、退款或广告来源 | 币种/周期/估算口径；平台核价动作另查实现 |
| 订单/采购/售后 | 既有页面、API 域及状态组件 | 订单异常直达采购、发货或售后处理 | 物流数据真实性；备货与销售订单不能混为一谈 |
| AI | 行动中心、副驾驶、依据与工作流页面 | 建议→证据→审核→执行→结果回看 | 会话持久化、Agent 运行等能力逐项确认，未接入不造入口 |

## 4. 面向谁，先完成什么

| 用户 | 默认看到 | 首要旅程 | 必须避免 |
|---|---|---|---|
| 个人新手 | 今日任务、继续准备/上线 | 已有商品或选品起步→连接店铺→补资料→启动上线→完成当前人工事项 | 强迫先理解 Listing、工作流模板、核验状态等内部概念 |
| 专业运营 | 可保存筛选的任务/商品/上线列表 | 多商品多店筛选→批量准备→逐项处理阻断→核对结果 | 将“批量选择”误做成忽略差异的一键全部发布 |
| Owner/管理者 | 经营异常、待决策、利润口径 | 发现风险→看证据→批准/拒绝→回看效果 | 所有操作都堆在老板首页；敏感审批没有上下文 |
| 合规审核人 | 授权范围内的材料审核队列 | 看材料→核验依据→决定→可追溯历史 | 要求通用写权限才能做专属审核 |
| 工厂协作者 | 与自身工厂有关的供给/任务 | 看数量与期限→上传实物/备货证据→提交 | 暴露销售利润、全店铺数据或通用 Launch 管理 |
| 平台管理员 | 独立平台控制台 | 管理空间、能力及审计 | 与商家导航混排，代客后不清楚当前身份 |

优先旅程 J1：商品→店铺→Launch→缺资料→补材料→回到原步骤→继续。
优先旅程 J2：今日待办→对象证据→人工决定/审批→结果→待办更新。
优先旅程 J3：在售商品→经营异常→利润依据→提出动作→执行回执。
优先旅程 J4：订单异常→采购/备货/履约→处理结果→售后/结算关联。
J1/J2 未验收前，不以新增更多分析页、预测页或设置页作为主要进度。

## 5. 信息架构与页面关系

保留 V9 的 8 个业务域，首轮不重新发明分类名称。整改重点是默认展开范围、常用入口、页面之间的上下文和主次层级。

- 顶栏：Workspace、当前店铺范围、任务提醒、帮助和账号。始终让用户知道操作作用于哪里。
- 日常优先入口：工作台、我的待办、商品库、上线中心、订单。专业用户可固定常用入口；必须仍通过权限过滤。
- 商品域默认优先商品库/上线中心；市场机会/候选池为准备阶段入口；Listing、素材、合规保留专业入口并可从商品/步骤直达。
- 设置置底；Factory/Console 保持独立空间，不混入商家业务侧栏。
- 待接入能力不占日常菜单，不做“点进去才知道不能用”的占位页；可在独立能力说明中查看。
- 同一对象只有一个主详情地址；卡片/抽屉用于快速预览，复杂编辑进入完整详情。旧链接保留参数和安全返回路径。

全站导航规则：任务中心负责找事；商品详情负责看对象；Launch 负责推进上线；专业页面负责完成具体业务。不得四处重复同一套编辑表单。

## 6. 核心页面详细设计任务

### 6.1 经营工作台

首屏：左侧“今天需要你处理”的 3—5 项高优先任务；右侧经营阶段与唯一推荐入口；上方小型计数条区分待我处理/等待外部/被阻断。排序依据为时限、风险、责任与阻断程度，不由 LLM 自由决定。

第二屏：进行中的上线摘要、关键经营指标。AI 已完成记录作为可展开活动流，不与待办抢主位。趋势图移到经营分析入口或下方，不让新用户先看一屏无数据图表。

每条任务包含对象、店铺、原因、责任人、时间、主操作。计数卡点击打开相同筛选的完整清单。数据源失败显示未知/部分可用，不能变成 0。

### 6.2 我的待办

从按来源堆卡片改为统一任务列表；默认“需要我处理”，附等待外部、受阻、已完成视图。支持商品/店铺/类型/期限筛选，保留 URL 条件与返回位置。

相同业务事项只展示一次，保留来源追溯。若后端当前仅返回分组摘要，先增加只读聚合明细契约，不在前端捏造任务实例、负责人或截止时间。

### 6.3 商品库与商品详情

商品库默认列：图片/SKU/名称、准备度、货源和成本状态、渠道数量、上线摘要、风险、下一动作。列可配置，筛选可保存并按 Workspace 隔离。主操作依据对象状态选择“准备上线”“继续上线”或“查看经营”。

商品详情顶部：商品身份、主档准备度、目标店铺提示、主要操作。主体采用概览/货源/销售渠道/上线进度/经营表现/合规与素材/AI 建议/历史 Tab，按需加载，不一次请求全部数据。

销售渠道行：店铺+市场、派生 Listing、活跃流程、外部事实、最近核验、下一动作；历史轮次单独展开。未开始的目标店铺是否展示由真实授权店铺清单补足，不能从空 channels 推断所有平台都无商品。

旧版的货源、评分、定价、合规和经营信息建立迁移对照，禁止新版“页面更清爽”却删掉既有业务能力。

### 6.4 上线中心与详情

列表：默认待处理，展示商品、目标店铺/市场、阶段、完成数、阻断、责任人、下一动作与更新时间；提供等待平台/待人工/失败/已上线等视图。状态不单靠颜色表达。

创建向导：选择商品→选择店铺→预检查与流程说明→启动。允许先建草稿再补齐资料；启动条件由后端决定。多店创建须逐店说明流程和结果，不混成一条发布记录。

详情布局：顶部商品/店铺/进度/主要阻断；左侧阶段导航；中间当前任务及所需材料；右侧精简证据与 AI 建议。较窄屏幕将右侧收为抽屉。并行分支用分组显示依赖，不硬编码某平台的固定十步。

Guided：优先一项可执行动作，明确“需要你操作”或“等待平台，无需操作”。Professional：展开外部状态、核价、成本、版本、同步和审计，同一数据源与权限。

动作完成后显示“什么改变了、仍缺什么、下一步是什么”。冲突先刷新合法动作，保留用户输入；失败重试不能盲目复用失效 revision 或已完成动作。

### 6.5 素材、合规、标签

从商品/Launch 进入时继承商品、店铺、市场、步骤与返回路径。素材采用缩略图+用途+权利+核验+版本+适用范围；原始素材、加工图、授权证明有明确关联。

登记与核验分成不同操作。不能把所有个人用户素材强制升级为双人审批；遵循现有权利规则。核验权和普通编辑权分开。

文件上传、摘要计算、存储和内容核验若后端未支持，列为服务缺口；不让用户靠随便填写 hash 完成看似成功的上传。

合规按市场显示“要求/已有材料/状态/有效期/缺口”。标签显示来源材料与版本，预览后才生成/下载；认证标记不能由 AI 猜。证据被驳回时显示具体理由和补交入口。

### 6.6 其余页面的整改范围

| 页面域 | 改造任务 | 交付标准 |
|---|---|---|
| 市场机会/候选池 | 来源与更新时间、选品依据、候选比较、带上下文转商品/找货源 | 不重复录入来源；AI 判断与外部事实分开 |
| 店铺与渠道 | 授权状态、市场/经营模式、可用能力、同步健康、配置缺口 | 连店成功不等于所有操作可用；可直接处理授权或同步问题 |
| 供应商/采购 | 商品关联、报价有效期、数量/交期、风险、采购单进度 | 从缺货/备货任务带入数量和商品，返回原流程 |
| 订单/售后 | 按异常及处理优先级组织；详情集中关联采购、履约、退款和结算 | 不让用户靠多个 ID 手工搜索；未知物流不伪造轨迹 |
| 定价/广告 | 利润构成、敏感成本、建议影响范围和审批结果 | 明确币种/时间窗/估算；成本变化可追溯 |
| 财务/分析 | 从异常金额下钻到来源；展示未归因费用、数据缺口及估算 | 不将缺失数值当零，不将不同币种直接相加 |
| AI 行动中心 | 建议、依据、风险、适用对象、审批/执行状态、结果反馈 | AI 建议不是已执行；从业务页跳来保留对象上下文 |
| 工厂门户 | 只展示自身相关供给及真实协作任务 | 没有任务 API 时说明缺口，不借商家接口扩大范围 |
| 平台管理 | 空间、能力、审计分区；代客身份持续可见 | 与商家操作隔离，退出代客恢复原身份 |

## 7. 共享交互和前端工程

复用并修正 PageHeader、SectionState、BusinessStatus、MoneyValue、TaskCard、EvidencePanel、NextActionPanel、AsyncActionDialog、WorkflowStepper 等既有组件，不再为同义场景创建另一套组件。

统一契约：

1. 页面抬头回答“哪个对象/什么范围”；每个操作区一个主操作，其他操作分级，不限制列表每行都有自己的主操作。
2. 状态分为页面加载状态、业务流程状态、外部平台状态、数据可信度四层，不能把所有枚举混进一个颜色字典。
3. 金额带币种，百分比有分母和周期，未知用“—/尚未获得”，估算标估算。
4. 表单字段错误就地展示，整体错误显示可理解原因；403 不显示为空，409 保留输入，超时提供查询结果再重试。
5. 跨页上下文包含 product/shop/run/step/return_to 的适用部分；服务端重新验证，return_to 只允许站内合法路径。
6. Workspace 切换取消旧请求并清理旧列表、缓存、所选店铺和批量选择；迟到响应不得覆盖新空间。
7. 查询状态放 URL；保存视图按用户与 Workspace 隔离。浏览器返回后恢复筛选、页码和滚动位置。
8. API 域适配层使用真实响应样本做契约测试；组件只消费稳定 ViewModel，不散落猜测 items/data/channels。
9. 风险动作只在有实际决策意义时确认，展示对象和影响范围；普通保存不增加多余确认。
10. 桌面操作保持合理密度，默认正文 14px 左右、清晰层级；通过键盘可完成筛选/表单，焦点可见，图标有文字说明。

不以引入新 UI 库、全量 TypeScript 迁移或重建状态管理框架作为本轮前置条件。

## 8. 实施批次与派工

所有“完成”均要求页面真实操作证据，不以文件存在或单测数代替。

| 批次 | 工作包 | 负责人类型 | 依赖 | 交付及退出条件 |
|---|---|---|---|---|
| R0 | 当前代码/产物/入口/未提交改动归属；全菜单和写操作契约盘点；复现 E01—E12 | 前端负责人+后端接口负责人+QA | 无 | 形成唯一现状清单；标注已可用、错接、缺 API、占位、待验证 |
| R1 | 修素材/渠道 DTO、路由重复、错误吞没、动作权限与上下文 | 前端+后端配合 | R0 | 商品→渠道→Launch；素材读/登记/核验按角色真实通过及拒绝 |
| R2 | 工作台、任务、商品详情、Launch 四类页面交互原型及共用骨架 | 产品/设计+前端负责人 | R0，可与 R1 部分交错 | 用空、新手、多店、受阻、无权限数据审阅；关键任务不靠口头解释可找到 |
| R3 | 实现 J1/J2 主闭环；原型落地真实 API；统一材料/操作/返回链 | 前端主流程组+领域后端+QA | R1、R2 | 简单/复杂 Profile 各一条隔离环境旅程通过，人工补资料后可继续 |
| R4 | 供应采购、订单售后、定价财务、AI 结果回看 | 各业务前端+领域负责人 | R3 共用契约 | J3/J4 及专业角色旅程通过；能力缺口有明确后端任务 |
| R5 | 全站视觉/响应式/键盘/性能整改、角色隔离、回归、灰度和切换 | QA+前端负责人+发布负责人 | R3、R4 | 浏览器验收、业务一致性及回退演练完成，用户对核心旅程验收 |

建议最小分工：1 名产品/交互负责人统一业务路径；1 名前端负责人拥有路由/组件/接口适配契约；业务页面按对象分包；1 名后端接口负责人；QA 从 R0 参与。人数不足时顺序执行，不用未核实的人天数字承诺工期。

共享文件（路由、导航、权限、状态字典、tokens、API 公共层）由单一负责人管理；其他工作包按契约提交。前端发现后端缺口时建立独立任务，禁止擅自改变领域规则。

每个派工卡必须包含：用户场景、现状证据、改动页面、真实 API/权限、成功路径、异常路径、依赖、验收录像/截图/网络请求、回退范围、遗留项。不得只写“优化某页面”。

## 9. “好用”的验收标准

以下是拟定门槛，R0 测旧版/V9 基线后确认；不是已测结果。

| 维度 | 验收办法/门槛 |
|---|---|
| 能找到 | 至少 3 名未参与实现的代表用户，从首页找到待处理上线流程，目标 30 秒内；需要提示的步骤必须记录 |
| 能完成 | J1/J2 本地可控部分在不口头指导下完成率目标 ≥90%；外部等待计为准确进入等待态，不冒充真实上线 |
| 少绕路 | 从商品到对应店铺 Launch、从待办到处理对象，均 ≤2 次导航；不需复制 ID 或重新选择已有上下文 |
| 不丢功能 | 旧功能清单每项记录复用/迁移/合并/暂缓原因；已授权关键能力无意外消失 |
| 不误导 | 0 个把错误当空、未知当零、提交当在售、建议当执行、未授权当已接入的核心路径 |
| 角色正确 | Owner、Operator、Read-only、Compliance、Factory、平台管理员逐一覆盖；跨空间/店铺数据不泄露 |
| 异常可恢复 | 401/403/409/422/超时/部分数据/撤权/重复点击均有可理解反馈；刷新返回后不丢关键上下文 |
| 真实密度 | 无数据、单商品、同商品双店、多页商品、多任务、长名称、长错误、失效素材均实测 |
| 视口 | 1440×900、1366×768 桌面完成核心操作；768 与390宽度可阅读及处理简单待办，复杂表格合理横滚 |
| 性能 | 同设备同数据对照，记录首屏/路由/接口耗时；目标本地受控条件主内容 ≤2秒，无因加载全部 Tab 导致明显卡顿 |
| 工程 | 受影响组件交互测试、真实响应契约测试、隔离后端浏览器 E2E、现有回归/构建通过；不降低断言 |
| 部署 | 验收产物与正式入口 build 身份一致；深链刷新可用；实际回退演练不改业务事实 |

浏览器旅程至少覆盖：新用户准备上线；双店独立进度；低价决策；材料缺失/过期/驳回；人工完成后返回；等待平台；重复提交/冲突；审批后撤权；Workspace 切换；只读/合规/工厂隔离；经营异常追溯；订单售后关联。

测试数据使用隔离库并标识来源；仅 Contract Profile 的外部事件可用测试契约模拟，不能记为真实平台验收。浏览器操作、截图和网络证据必须来自实际页面；设计稿不能替代。

## 10. 切换、回退与项目收口

先在独立验收入口交付一条完整主流程供用户试用，接受反馈后扩展其余域。不要等几十页全部完成才让用户第一次使用。

切换前：核对旧链接、资产路径、刷新、权限、构建版本、Docker/静态托管、错误观测；备好旧产物。若涉及后端契约增量，明确版本兼容，不能假设单切静态文件即可回退所有业务行为。

切换后观察一个约定版本周期，再决定删除旧源码和旧构建链。回退切回已验证产物，保留新产生的业务事实与审计；数据库变更遵循独立迁移规则。

工程进度继续记录在 FRONTEND_V9_PROGRESS.md，本计划只管理 R2 目标与实施要求；不重写已有历史验收。每批记录代码提交、可访问入口、用户场景、实际验证及剩余缺口，避免“新增多少页”成为唯一成果。
