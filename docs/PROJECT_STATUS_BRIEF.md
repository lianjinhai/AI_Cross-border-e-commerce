## 1. 一页速览

### 1.1 这个项目是什么

**AI 原生跨境电商经营平台**——一个把「选品 → 供货 → 上线 → 履约 → 算钱 → 用 AI 优化」串成一条可执行工作流的经营操作系统。

技术上是**单体模块化 + 多租户**的一套前后端：后端 FastAPI，前端两套（旧版可回退、V9 为重建版），AI 能力由「领域能力 Agent + 工具 + 服务 + Action 审批执行」组成。

### 1.2 这个项目不是什么（重要，避免误解）

| 常见误解 | 实际 |
|---|---|
| 「聊天机器人」 | 不是。AI 只出建议与 Action 提案，业务写入必须经 Policy / Permission / Risk / Approval 闸门后由执行器落库 |
| 「自动铺货工具」 | 不是。核心价值是判断与流程管控（合规门禁、成本口径、证据追溯），不是批量刷 listing |
| 「任意平台任意类目都能全自动上线」 | 不是。平台能力按适配器声明，未实现的平台前端禁用、不做假实现 |
| 「页面做完 = 功能通了」 | 不是。项目验收分四层证据（代码 / 自动化 / 真机系统 / 业务），前一层通过不自动通过后一层 |

### 1.3 现在到哪一步

| 主线 | 状态 |
|---|---|
| 业务域能力（商品 / 供应链 / Listing / 合规 / 定价 / 广告 / 订单 / 售后 / 结算 / BI） | 已有可用存量实现，主干链路可跑通 |
| 前端 V9 全站重设计（UX-A…UX-F） | 设计冻结 + 全部阶段完成 + 终验通过，**具备切换条件** |
| 前端 V9.1 正确性/闭环批次（B1–B3、S3–S5） | 已提交：统一外壳与令牌、经营画像持久化、选定报价闭环、AI 能力矩阵、AI 内部业务链、订单详情聚合 |
| Launch Center（复杂上线生命周期） | 设计冻结（FROZEN_FOR_IMPLEMENTATION），实现为 **P0 部分完成**，领域服务（核价 / 备货 / 素材 / 标签）与前端同页双模式尚未开工 |
| 真实平台联调 | **未进行**。协议按官方文档实现，部分平台标注 `protocol_ready_unverified`；Amazon 能力清单全空 |
| 生产化基础设施 | 未做。单库单体，无 Redis / 队列 / K8s |

### 1.4 还缺什么（一句话版）

硬缺口集中在「上线生命周期的领域动作」与「外部真实联调」：市场级证据对象、询价发送、批量经营聚合、平台授权账号、真实资金与物流对接。详见 §6。

## 2. 项目定位与技术栈

### 2.1 定位

基于《需求分析与详细设计说明书 V8.0》演进而来，但已经越过「按章节实现规划书」的阶段：当前主线是**让用户能完成真实任务**（找到/录入商品 → 明确供给成本 → 选店铺 → 按平台流程上线 → 处理审核 → 核验在售 → 履约与经营监控 → 基于证据优化）。

三条差异化能力：

1. **LLM / 规则双模**：每个 Agent 方法统一走 `ask_json()`；有 API Key 走大模型，任何失败无缝降级确定性规则引擎。**离线零配置可完整运行**，接模型后同一套代码自动升级，且来源如实标注 `llm` / `rule`。
2. **合规门禁（防封店）**：发布前三道关——平台规则包强制校验 → 平台必填字段校验 → 类目映射校验，任一不通过拒绝发布并给出原因。
3. **多租户 SaaS**：业务表带 `tenant_id` 强制过滤；平台超管控制台与租户业务菜单完全隔离；代客访问留审计。

### 2.2 技术栈

| 层 | 技术 | 备注 |
|---|---|---|
| 后端 | Python 3.11 + FastAPI + SQLAlchemy 2.0 + Pydantic v2 + PyJWT + Alembic | 依赖见 `backend/requirements.txt` |
| 数据库 | SQLite 开箱即用（`backend/erp.db`），`ERP_DB_URL` 可切 MySQL / PostgreSQL | 结构变更只走 Alembic |
| 前端（旧） | Vue 3 + Vite + Element Plus + ECharts + axios | 目录 `frontend/`，可回退基线 |
| 前端（V9） | 同上栈，重建外壳与页面组织 | 目录 `frontend-v9/` |
| AI | OpenAI 兼容 Chat Completions（GLM / DeepSeek / OpenAI / Ollama 皆可）+ 可选 embeddings 检索 | 无 Key 时全链规则兜底 |
| 认证 | PBKDF2 口令散列 + JWT HS256 | 静态盐属 MVP 简化 |
| 部署 | Docker 多阶段构建 + docker-compose（可选 MySQL profile）+ Caddy（TLS 方案） | 见 `Dockerfile`、`docker-compose.yml`、`Caddyfile` |
| CI | GitHub Actions：后端 pytest + 前端构建 | 见 `.github/workflows/ci.yml` |

### 2.3 分层与依赖红线

```
routers/  →  agents/  →  tools/  →  services/  →  models.py
```

| 红线 | 内容 |
|---|---|
| L-1 | `services/` 禁止 import `routers/` |
| L-2 | `agents/` 禁止 import `routers/` |
| L-3 | `agents/` 之间禁止互相调用，只能由 Orchestrator 编排 |
| L-6 | 禁止用函数体内延迟 import 掩盖循环依赖 |

Agent 层额外红线：不得临时创建 Agent、不得直接操作数据库、不得绕过权限执行动作、禁止无 Workspace Context 运行。

## 3. 业务主链与功能全景

### 3.1 业务主链

```
市场发现 → AI 选品 → 供应商/货源 → 利润与到岸成本 → 合规检测 → Listing 生成
→ 一键铺货/上线 → 广告增长 → 动态定价 → 订单处理 → 客服售后 → 账期结算 → BI 经营分析
```

### 3.2 十大功能模块

| 模块 | 已实现的核心能力 |
|---|---|
| 商品采集 | 三层采集管线（1688 官方 API → 静态 HTTP 解析 → Playwright 无头浏览器），粘贴源码兜底；SSRF 防护；验证码页识别；订单/商品 CSV 导入导出 |
| 选品发现 | 趋势扫描、关键词扩展、机会评分（需求/竞争/利润/风险四维加权）、趋势候选池 |
| 供应链采购 | 补货预警 → 一键生成采购单 → 提交供应商 → 收货入库；报价单录入；私域工厂建档与门户 |
| Listing 与发布 | 多语言文案生成/优化；发布前三道合规关；店铺派生稿；发布回执与尝试记录 |
| 合规 | 商标侵权 / 违禁宣称 / 图片风险 / 平台规则四维扣分；报告与整改建议；复核队列与人工裁决 |
| 广告 | AI 选词、预算 ROI 优化（>2 加预算 / <0.8 降预算）、ROI 报告 |
| 订单与发货 | 筛选、同步（source 标注 demo/api）、CSV 导入导出、一键发货、状态流转、详情聚合（行/费用/采购/退款/履约） |
| 售后逆向 | 退款单全状态机（待审核→已同意→已退货→已退款/已拒绝）；重复退款拦截；按数量比例校验金额；退货入库回补库存 |
| 账期结算 | 供应商账期（15/30/45 天）对账单生成 → 确认 → 标记付款；应付账龄总览 |
| BI 分析 | 统一 GMV / 净收入 / 贡献利润 / ROAS / ROI / 退款率；数据质量门禁；AI 经营报告 |

### 3.3 平台接入层

差异全部内聚在适配器，注册表在 `backend/app/services/adapters/registry.py`：

- **销售平台**：Shopee（真实上架两步走：图片预上传 → product/add_item）、TikTok / eBay / Lazada / Walmart（协议按官方文档实现，标注 `protocol_ready_unverified`）、1688（货源平台，`can_publish=False`）。
- **Amazon**：能力清单全空，前端自动禁用，**不做假实现**。
- **授权双通道**：公网回调 OAuth 与本地「粘贴授权码」等价，便于无公网开发。
- **规则包**：内置规则包是**人工整理的快照**，带版本日期与来源链接，不是平台实时下发；支持库内覆盖与远程规则源。

### 3.4 前端两套口径（易混淆，务必分清）

| 项 | 旧 `frontend/` | `frontend-v9/` |
|---|---|---|
| 页面组织 | 24 个业务页 + 登录 | 16 个页面域，V9 冻结口径为 30 界面 |
| 信息架构 | 5 组侧边栏菜单 | 11 业务域 + 平台控制台 / 工厂门户两个独立域 |
| 当前地位 | 可运行、可回退基线 | 已完成 UX-A…F 全阶段与终验，具备切换条件 |

**关键运行事实**：8000 端口默认仍托管旧 `frontend/dist`。要让用户真正看到 V9，必须设置环境变量 `ERP_FRONTEND_DIST` 指向 `frontend-v9/dist` 后重启后端，可用 `GET /api/build-info` 核对当前实际托管的是哪套前端。这是历史上「前端已开发但用户看不到变化」的根因，不要重复踩。

## 4. 建设路线与首发范围

### 4.1 里程碑（来源：`docs/PROJECT_MASTER_PLAN.md`）

| 里程碑 | 主要工作 | 放行标准 |
|---|---|---|
| M0 统一事实 | 工作区归属、能力/接口/页面清单、文档漂移、产物身份 | 未提交与已提交分开；无过期「未开发」结论 |
| M1 可用前端主线 | 契约修复、工作台/商品/待办/Launch 重组 | 不丢上下文、不显示假空态、权限正确 |
| M2 复杂生命周期 | 核价、备货、Artifact、标签、实物材料及事实接入 | 低价/缺材料阻断；版本与双店进度正确 |
| M3 可靠协同 | 外部状态映射、同步、事件投递、通知、恢复 | 不重复外部副作用，人工节点可追踪 |
| M4 经营与 AI 闭环 | 订单/售后/利润贯通，Agent 写路径与 Action 结果 | 指标可追溯，建议不越权执行 |
| M5 试点交付 | 指定账号/市场联调、端到端、迁移副本、浏览器体验、构建与回退 | 清楚列出支持范围与未接能力 |

### 4.2 首发业务边界

优先验证「**已有商品/供给的用户完成上线**」，再扩展市场机会驱动的选品路径。原因是这条路径可直接复用现有商品、店铺与 Launch 基座，所需外部变量最少。

### 4.3 明确不承诺

- 任意平台、任意类目均可自动上线。
- 无人工介入的全自动核价、认证、备货或退款。
- 全功能物流、支付、会计记账替代系统。
- 未核实数据源支撑的实时市场预测。
- 多副本分布式部署、复杂基础设施或第三套前端。

### 4.4 验收体系（四层证据，不可越级）

1. **代码证据**：实现、字段、权限、状态与迁移真实存在。
2. **自动化证据**：单元、契约、并发、迁移、回归测试。
3. **系统证据**：隔离后端 + 真实浏览器 + 构建产物的用户操作。
4. **业务证据**：限定授权店铺 / 市场 / 类目的外部结果与用户可用性。

## 6. 已知边界与硬缺口

### 6.1 硬缺口（做不到就是做不到，不要用前端勾选绕过）

| 缺口 | 影响 |
|---|---|
| 市场级证据对象（SKU × 目标市场的材料/认证/标签依据） | 复杂 Profile 的核价与合规节点无法完整推进 |
| 询价发送（向供应商发起询价的动作与回执） | 货源环节只能停在「比较已有报价」 |
| 跨店/全量经营聚合 | 首页工作台已做只读聚合，但缺少独立的经营总览聚合端点 |
| 平台授权账号与真实店铺 | 所有外部联调当前都是契约测试 + 浏览器验证，不是真实平台结果 |
| 真实资金与物流 | 退款真实打款由平台侧完成；发货 `tracking_no` 为系统生成，未对接面单 |

### 6.2 语义红线（最容易写错的地方）

- **`settlements` 是供应商应付对账，不是平台回款或 GMV。** 不得当成营业额口径。
- **`WAITING_EXTERNAL` 不得写成「已上线」**：等待外部平台回执与核验在售是不同状态，混写会误导用户做错误决策。
- **未接入能力一律显式标注「未接入」**，不放可点击入口，禁止只有 409 的按钮，禁止伪造成功。
- **货币口径**：有 `currency` 就绑定显示；没有就显「—」或「—（口径未知）」，**禁止默认 `$`**。
- **数据来源必须可辨**：`demo`（模拟）/ `api`（平台真实拉取）/ `local`（仅本地置状态）/ `rule`（规则引擎）/ `llm`（大模型）。

### 6.3 工程边界

- 单库单体：SQLite 开箱即用，未引入 Redis / 消息队列 / K8s；调度器与工作流用进程内线程。
- RAG 为轻量实现：embedding 存 SQLite JSON 列 + 余弦相似度，未用向量数据库；检索接口已抽象，可平滑升级。
- 图片合规为规则启发（空图 / 水印关键词），未走多模态模型。
- 规则包是人工整理的快照，商用前必须核实各平台最新官方文档。
- 跨境到岸成本内置税率/费率是代码内参考值，非官方实时数据；未维护税率表时按 0 费率，不能据此认定利润已完整。
