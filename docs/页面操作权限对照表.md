# 页面-操作-权限 key 对照表（实施依据）

> 权威事实源：`backend/app/services/workspace_context.py` 的 `ROLE_PERMISSIONS`
> 前端查询：`workspace.js::hasPermission(key)` ← Context 的 `permissions[]`
> 本表是实施与验收对照；权限以服务端矩阵为准，禁止凭感觉映射。

---

## 一、权限 key 全量（现有，来自后端）

### 读权限（12 个，`_READ_PERMISSIONS`）
`workspace:read` `product:read` `supply:read` `listing:read` `order:read` `finance:read`
`purchase:read` `settlement:read` `refund:read` `compliance:read` `ai:read` `support:read`

### 写权限（10 个，`_WRITE_PERMISSIONS`）
`workspace:write` `product:write` `supply:write` `listing:write` `order:write` `finance:write`
`purchase:write` `settlement:write` `refund:write` `ai:write`

### 特殊权限（现有 2 个）
`workspace:member:admin`（成员管理） `compliance:approve`（合规审批）
### 新增（本轮，复核修正 9）
`compliance:check`（发起合规检测）—— `ROLE_COMPLIANCE`、`ROLE_OWNER` 与 `ROLE_OPERATOR` 均持有

---

## 二、角色-权限矩阵（后端权威）

| 角色 | 权限集 |
|---|---|
| **OWNER**（admin） | 全部读 + 全部写 + `workspace:member:admin` + `compliance:approve` + `compliance:check` |
| **OPERATOR** | 全部读 + 全部写 + `compliance:check` |
| **READ_ONLY**（viewer） | 全部读（12 个） |
| **COMPLIANCE** | `compliance:read` `compliance:approve` `compliance:check`(新) `listing:read` `product:read` |
| **PLATFORM_ADMIN** | `platform:admin`（无业务权限） |
| **FACTORY_COLLABORATOR** | `supply:read` `supply:write` |

## 四、验收标准

| # | 验收项 | 方式 |
|---|---|---|
| 1 | 后端 `ROLE_PERMISSIONS` 与前端 `can()` 判断一致 | 一致性测试（读取后端矩阵 + 断言前端 key 存在） |
| 2 | 每个页面的写操作都有权限控制 | 覆盖率测试（grep 页面写操作 + 断言有 `can(`） |
| 3 | 6 角色 × 关键页面按钮可见性正确 | 浏览器实测 |
| 4 | viewer 在任何页面看不到写按钮 | 浏览器实测（重点） |
| 5 | COMPLIANCE 可发起检测、可审批，但不能发布 | 浏览器 + pytest |
| 6 | FACTORY_COLLABORATOR 仅门户可用，写操作受 `supply:write` | 浏览器实测 |
| 7 | 全量回归不破坏存量 | pytest |

## 五、明确不做

- ❌ 不新建前端角色-权限矩阵（会与后端 `ROLE_PERMISSIONS` 双事实源）
- ❌ 不引入 `v-permission` 自定义指令（15 页用 `v-if="can()"` 已足够）
- ❌ 不重构 Context 体系（工作良好）
- ❌ 不改变后端权限模型（仅新增 `compliance:check` 一个 key）
