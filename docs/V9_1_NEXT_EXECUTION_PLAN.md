### S1：B3 选定报价、成本与详情收口

**后端主文件：** `backend/app/routers/products.py`、`backend/app/routers/suppliers.py`、`backend/app/services/costing.py`、`backend/app/models.py`；迁移核对 `backend/migrations/versions/20261019_30_offer_selection.py`。迁移是否已执行必须先查，已执行文件只增补迁移不修改。

**前端主文件：** `frontend-v9/src/pages/supply/Matching.vue`、`frontend-v9/src/shared/matchingView.js`、`frontend-v9/src/api/domains/products.js`、`frontend-v9/src/api/domains/pricing.js`、`frontend-v9/src/pages/product/ProductDetail.vue`、`frontend-v9/src/shared/productDetailView.js`。

工作分四组：

1. **选定规则**：按商品保存优先采购报价；服务端验证归属、是否对应同一商品、可用性、版本及操作权限。重复 PUT 幂等。未选时候选报价规则必须明确，跨币种只在合法换算后排序。失效选定不静默包装为用户选择；自动回退若保留必须显式说明实际采用报价和原因。
2. **成本上下文**：Product 选择只是采购来源，不代表全部 Store 的运费、税费、平台费相同。成本请求/响应明确商品、报价、目标 Store/市场、数量和费用口径；服务端校验店铺归属。没有目标上下文时只允许通用试算并列出未知项，不能展示某店铺的确认利润。
3. **成本证据**：响应包含或可追溯采用的 offer_id、报价币种、换算依据/时间、费用分项、完整性、计算版本/时间和假设。版本机制复用既有规则；缺少时补齐有意义的版本/输入指纹，不能前端编个编号。报价/选择/费用变更后成本失效或重算，前端丢弃旧请求迟到响应。
4. **交互一致性**：写入失败保留原选择；写入成功但读回失败显示“已提交，确认结果失败”，不重新发送可能已成功的写操作。重新查询成功后才展示确认状态。多币种不可直接比数字。Overview 部分失败保留已知数据并标过期/失败，不能显示假完整；按钮全部有可达目标，询价复制不称已发送。

选定失效规则先写进契约并测试：删除/不可访问必须失效；过期、缺货和未核验分别区分“允许保留偏好”“允许试算”“允许采购/上线”。缺少业务批准条件时保留偏好但阻断对外承诺，不凭前端标签把它变成有效报价。若确需业务方决定宽限期等规则，只询问该项并推进其余工作。

测试入口：`backend/tests/test_selected_offer.py`、`backend/tests/test_product_overview.py`、`backend/tests/test_pricing_outputs.py`、`backend/tests/test_store_scope.py`、`backend/tests/test_security.py`；`frontend-v9/tests/shared/matching.test.js`、`frontend-v9/tests/product-detail-view.test.js`。按具体变更新增 API/交互断言，不用源码字符串存在性代替行为验证。

门槛：三报价可选/清除/改选并读回；Costing 的 offer_id 与实际使用金额可证明一致；两店铺成本上下文不串；所有缺失费用仍可辨识。

### S4：跑通一条最小 AI 内部业务链，再扩展

首条目标建议采用“依据当前商品资料生成可审核的销售内容草稿”。先核对可用链，优先选择已注册的 UPDATE_PRODUCT_CONTENT 或 CREATE_LISTING_DRAFT 之一；不需要同时造新动作，不把人工直接创建 Action 当最终 AI 验收。

链路要求：

1. 用户从真实商品或任务入口提交目标，服务端装载身份、Workspace、店铺范围及能力。
2. Orchestrator 按已验证 Planner/路由调度领域 Agent，Agent 经 Tool 获取可信事实；不直接读写数据库、不自由调用其他 Agent。
3. 模型返回结构化建议和证据引用，服务端做 schema 与业务校验；模型输出不直接执行代码、URL 或任意工具。
4. 分析产物由可信产物服务持久化；需要业务修改时生成既有 Action，记录原始依据、目标、预期影响和关联任务。
5. Policy、Permission、Risk、Approval 按现有策略执行。低风险 AUTO_SAFE 不凭空增加审批，高风险不省略审批。另选一个策略本就需审批的动作验证 approve/reject 分支。
6. Executor 幂等调用既有领域服务，读回修改前后业务对象，产生可查询回执；刷新后任务/Action/业务事实一致。
7. workbench 与任务详情从统一事实源刷新：完成的建议不再作为未处理，残余阻断仍保留，下一步能进入正确对象。

失败处理：模型超时/限流/无效结构不造成功建议；权限收回/数据变化/冲突阻断执行；重复请求复用既有任务/Action 或给明确冲突；未知执行结果先查回执。服务重启后的任务恢复规则必须可测试，不能永远停在 EXECUTING。

验证分两层：受控模型 fixture 覆盖异常；另以已配置且授权可用的真实模型验证结构化输出链。未经授权不使用新外部账号或额外付费服务，缺条件时标明模型实测阻断，不把 fixture 宣称真实 AI 成功。

门槛：至少一条模型驱动的内部动作完整闭环及一条审批拒绝/通过路径；业务对象真实变化且可重读；跨域待办同步；无越权/重复副作用。若真实模型条件缺失，只能判内部编排联调通过，真实 AI 验收待完成。
