# AI 跨境经营平台 V9.1 — R3 目标驱动式前端重构总蓝图

> 版本：R3 / 产品与工程实施基准候选  
> 编制日期：2026-10-14  
> 依据：用户提供《UI_REFACTOR_BLUEPRINT.md》（R2）、此前 V9/V9.1 产品目标及项目已报告的能力边界。  
> **证据边界：**本文件评审 R2 的静态源码审计结论，并据此提出设计与实施决策；本次未连接用户本地 Git 仓库、未运行其前后端，也未验证当前数据库、外部平台或真实浏览器。凡“已存在/疑似错接”均须在 R0 用运行证据复核。  
> **重构授权解释：**允许大幅重做前端产品模型、信息架构、路由、布局、组件、前端 BFF/聚合适配层和必要的增量后端契约；不等于允许擅自清库、变更正式授权、自动支付采购、覆盖他人未提交代码或直接停产切流。

---

## 0. 最终执行决定（ADR-R3）

1. **不创建 `frontend-v10` 或第三套前端。**在现有 `frontend-v9` 上重构；旧 `frontend` 仅作回退、功能对照。开发期间新旧可以并存，不长期双线业务开发。
2. **产品默认从“8 域 ERP 功能目录”改成“4 个经营工作区 + 1 个专业工具柜”。**8 域可作为专业工具内的分类，不再当作新手的一级导航。
3. **用户面向目标、商品、订单、收益工作。**商品由市场机会、货源、成本、店铺、素材、Listing、合规、Launch、销售结果组成一个连续工作台；内部实体绝不混为一表。
4. **任务驱动而非菜单驱动。**一个任务有业务对象、可信状态、责任主体、原因、合法动作、证据、执行结果、返回位置；不通过 LLM“猜出”合法动作。
5. **先全局冻结体验契约，再纵向交付可跑通的用户旅程。**允许一次性大改路由/页面骨架，但不允许一次做出几十张静态 Mock 页面后宣称完成。
6. **技术断点先修。**R2 E01–E12 是第一批候选复现清单，首批优先修 E01–E06、E09、E10，不以换皮代替业务接通。
7. **AI 是嵌入式经营协作，不是总挂在右侧的大聊天框。**一切建议必须关联业务对象、版本、证据、权限和合法行动；AI不可充当外部平台核验或修改 Workflow 状态事实。
8. **所有测试与宣传必须区分：单元通过／Contract E2E／浏览器流程／平台真实环境验证。**前端可用不等于官方平台已接通。

## 1. 评审 R2：保留、强化、推翻

| 事项 | R2判断 | R3决定 | 执行含义 |
|---|---|---|---|
| 唯一前端基底 | `frontend-v9` | **保留** | 不开第三前端；仅一套正式路由与组件基座 |
| 业务服务、Workspace、Agent OS | 保留 | **保留** | 不复制订单、成本、合规、发布等服务，不改 Tenant=Workspace 边界 |
| E01–E12 契约缺陷 | 重点修复 | **升级为 P0 证据型门禁** | 真实 payload、401/403/409/422、多店/撤权测试 |
| V9 八大业务域 | 保留 | **改为内部专业分类** | 默认导航改 4+1，独立 Console/Factory |
| 首页结构 | 待办优先 | **进一步精简** | 上方只一项下一步 + 最多3项关键事项；专业模式可展开指标 |
| J1/J2 | 核心 | **保留并补 J0** | 零基础无货源/无店铺，从起点经过机会→货源→商品→渠道→Launch |
| 页面顺序 | 先接口→页面→流程 | **接口修复与统一任务/页面契约并行** | 防止修好旧页面又重做一次 |
| 商品详情 | 多 Tab | **改成三段经营内容 + 专业详情抽屉/子页** | 不强迫新手理解 8 个 Tab；仍支持所有原有字段 |
| Launch 中心 | 专业页 | **保留内核，降低入口复杂度** | 新手从商品的“继续准备销售”进入；专业人员可批量查Launch |
| 素材权利与核验 | 明确分离 | **保留并前置在发布前门禁** | `UNKNOWN` 权利绝不变成通过 |
| 浏览器与真实用户验收 | 完成门槛 | **加强用户任务可理解性验收** | 截图不等于可用；要测成功率、求助、误点击与耗时 |
| Docker/产物识别/回退 | 收口 | **正式发布门禁** | 运行 build ID 与 Git SHA、静态资源、回退演练一致 |

### 1.1 不做的三件事

- 不把“最简导航”理解成删除专业能力或把所有页隐藏到搜索里；专业工具仍是完整、可搜索、可收藏且权限可控的入口。
- 不把“业务任务聚合层”做成第二套 Domain/Workflow/Order 事实库。任务可以是 read model、projection 或持久化人工工单；必须追溯来源及去重规则。
- 不在无平台/数据能力时模拟真实市场需求、核价、广告转化率、认证或在售状态。

## 2. 用户认知模型：只理解“我、商品、订单、钱”

### 2.1 五个常用入口（个人/团队 Commerce Workspace）

| 固定主入口 | 用户听得懂的含义 | 默认内容 | 深层专业能力 |
|---|---|---|---|
| **我的生意** `/app/home` | 今天要做什么 | 当前目标、唯一主任务、紧急待办、经营摘要 | 工作台、自定义指标、经营路径、AI任务 |
| **我的商品** `/app/products` | 想卖什么、怎么卖出去 | 商品列表/候选方向、货源、销售准备、上架进度 | 市场机会、1688、工厂、Listing、合规、素材、Launch、定价 |
| **我的订单** `/app/orders` | 有单后怎么处理 | 订单/采购/发货/退款任务的一个工作区 | 采购、库存、物流、售后、平台备货 |
| **我的收益** `/app/earnings` | 卖了多少、真正赚了多少 | 可靠指标、费用缺口、结算、异常与改善行动 | 财务、BI、广告、定价实验、报告 |
| **全部工具** `/app/tools` | 我需要专业功能 | 按旧8域分组的搜索/收藏/授权专业功能 | 现有全部有用页面的明确归宿 |

顶部全局：Workspace 切换、店铺范围/市场（始终显示当前范围）、搜索、待办计数、AI帮助、通知、账号与设置。**“我的待办”是全局抽屉/完整列表的高频快捷入口，不再与四个工作区平级增加一个新一级菜单。**

`Guided` 与 `Professional` 是**同一 AppShell + 同一 API/实体/权限**的视图密度偏好。Guided优先任务卡、解释文字、渐进表单；Professional优先列表、批量、保存筛选、自定义列。切换不改变可执行动作、业务规则、工作区或身份。

### 2.2 独立门户

- **Platform Console** `/console/...`：平台运营、租户与能力、策略、监控、审计。平台操作身份清晰；需要代客时须显式进入审计模式。
- **Factory Portal** `/factory/...`：本厂 SKU、报价、库存、备货/标签、履约材料，只有绑定范围内的数据。Factory collaborator **不是**普通 Workspace Member。
- 管理员如同时是普通商户用户，两类权限及上下文独立选择，不自动串用。

### 2.3 路由与旧链接兼容

| 新用户入口 | 稳定领域对象路由示例 | 旧能力去向 |
|---|---|---|
| `/app/home` | `/app/tasks?tab=mine` | Workbench 聚合、原Dashboard | 
| `/app/products` | `/app/products/:id`、`/app/products/:id/launch/:runId` | 机会、供应、Listing、素材、合规、Launch工作台 |
| `/app/orders` | `/app/orders/:id` | 履约、采购、退款等上下文页面 |
| `/app/earnings` | `/app/earnings/analysis?store=...` | 结算、成本、广告与利润穿透 |
| `/app/tools` | `/app/tools/:group` + 旧专业路由 | 旧8域功能、批处理、规则与配置 |

以上是**目标路由**，不是已存在路由。实施时要对真实 Router 建唯一命中表，并通过兼容 redirect/alias 接住有权限的旧链接；禁止两个父路由同时声明 `channels` 造成抢占。跳转带 `product_id`、`shop_id`、`run_id`、`step_code` 与安全的 `return_to`，服务端再做权限验证。

## 3. 用户入场不是填写十几项资料，而是选起点

### 3.1 三条可持续经营路径

| 入口 | 首次主任务 | 不应该默认出现 |
|---|---|---|
| **零基础：没有货源、没有店铺** | 了解可承担的预算/市场 → 找方向 → 核实货源 → 试算 → 核实开店资格 → 首个商品准备 | 空销售图、复杂BI、财务审批表 |
| **已有货源/自有工厂** | 录入/导入SKU → 评估海外市场 → 核算交付与毛利 → 目标店铺与上线 | 反复要求去1688找货 |
| **已有跨境店铺** | 连接店铺 → 核实授权/同步能力 → 经营诊断 → 待办/优化 | 强制看新手起步问卷 |

个人/组织不是“新手/专业”的替代变量：企业可用 Guided，个人也可用 Professional。优先使用服务端 Capability Profile 的 USER_DECLARED/SYSTEM_OBSERVED/MODEL_ESTIMATED 证据等级；Business Stage 仍由版本化确定性规则计算。

### 3.2 零基础首次会话（最多6项核心问答）

字段与交互：

| 字段 | 控件/选项 | 必填与校验 | 写入与影响 |
|---|---|---|---|
| 我现在有什么 | 单选：什么都没有 / 自有商品或工厂 / 1688货源 / 已有店铺 | 必选，可回退 | declared starting_position |
| 打算卖到哪里 | 多选市场 + “暂不确定” | 不强制选国家 | 机会检索与渠道提示；未知不填默认海外站点 |
| 可以承担的试水预算 | 币种+区间 / 暂不确定 | 数值非负，币种显式 | 用于投资与履约可行性，不能当已付款资金 |
| 每周可投入的时间 | 区间/未知 | 可跳过 | 路线复杂度、任务拆分 |
| 有经验的事情 | 多选（拍摄、设计、运营、选品、供应链）/无 | 可空 | Capability USER_DECLARED |
| 最重视什么 | 单选（低投入/尽快验证/控制风险/利润空间） | 可跳过 | 任务排序偏好，不替代风险政策 |

CTA：`生成我的起步路线`（先保存资料、生成基于规则的阶段任务，不自动注册外部店铺）。次要：`稍后再说`（工作台显示“补充起步信息”任务），`修改`、`返回`。保存失败保持本地未提交草稿，401引导重新登录，409冲突合并前重新拉取资料。

### 3.3 路线进度不是百分比幻觉

- 进度只分母明确且已验证的可适用必做任务；对“选择市场”这种探索阶段可显示“完成1/4项准备工作”。
- “开店资格待核实”绝不等于店铺已连接；“平台提交成功”不等于ACTIVE；“有订单”不等于已到账。
- 用户可以跳过非强制研究步骤、暂停、改方向或同时研究两个商品；“未开始”“等待外部”“需要我做”区别明显。

## 4. 四个主页面：具体信息结构与动作

### 4.1 首页「我的生意」

**桌面主布局**（1440 宽）：

```text
顶部：Workspace ▾ / 店铺范围 ▾          全局搜索  待办(3)  AI  账号
┌──────────────────────────────────────────────────────────────┐
│ 你现在最值得完成的一件事：确认商品A的货源成本             │
│ 为什么需要做：缺物流报价，利润不可确认                     │
│ [继续这个任务] [查看依据]                                  │
├───────────────────────────────┬──────────────────────────────┤
│ 今天需要你处理（最多3项）    │ 我的经营阶段与当前路径         │
│ ① 商品A 缺供应商报价         │ 起步→商品准备→店铺→上线        │
│ ② 店铺B 授权即将失效         │ 显示可验证的完成条件           │
│ ③ 订单C 需要安排发货         │ 可切换经营目标                 │
├───────────────────────────────┴──────────────────────────────┤
│ 进行中商品/订单快览 | 有效指标（有真实数据时才显示）       │
└──────────────────────────────────────────────────────────────┘
```

字段：`primary_task`、`reason`、`target`、`actor`、`due_at?`、`evidence`、`available_actions`、`source_status`、`next_url`。服务端按到期、履约风险、合规、授权、阻断和任务归属计算优先级；AI解释优先级而非改写事实。页面聚合只读，单模块失败标记“部分数据暂不可用”，不能把未知计成零。第一次登录优先起步任务，不显示空的 GMV 面板。

### 4.2「我的商品」：**一个商品经营工作台，而非多个 ERP 页面**

**列表默认字段**：图片、商品名称/SKU、准备阶段、货源可信状态、预计利润可信状态、已关联销售店铺数、当前最关键阻断、主动作、最近更新时间。筛选：`准备中/在销售/待处理/归档`、目标市场、店铺、风险、数据缺项。高级模式扩展毛利、广告、结算、自定义列与批量合法动作。

**三个添加入口**：`我想找商品`、`我有现成商品/工厂SKU`、`从已有店铺导入`。起点不同，向导不同；不要求用户先学 Listing。

**商品详情默认三块业务区域：**

1. **商品资料与货源**：基础信息、规格、素材来源与授权、候选报价、生产/物流条件，CTA `补充商品资料` / `比较货源`。
2. **销售准备与平台进度**：每个Store独立行，显示目标市场、平台状态、现行Launch、资料缺项、合法下一步，CTA `开始准备销售` / `继续这个店铺的流程`。
3. **销售表现与优化**：真实订单、收入、可归属贡献利润及影响因素，CTA `查看经营表现`；无可靠财务事实时显示`暂无可核实数据`。

高级“更多详情”按需展开旧 Product/Listing/价格/合规/素材/历史全部信息；不得砍掉专业能力。

### 4.3「我的订单」：从待处理事件开始

默认四个子视图：`需要处理`、`处理中`、`已完成`、`售后`。每行显示平台/店铺、订单号、支付/成交时间（来源）、商品、金额+币种、承诺截止时间、履约方式、当前实际状态、阻断、主操作。订单详情显示：销售订单 → 对应采购或平台备货 → 发货/物流 → 售后/退款 → 结算/利润相关项（只读）。

CTA根据真实条件切换：`确认货源`、`安排采购`、`上传凭证`、`提交发货`、`处理退款`；涉及付款、承诺或平台操作走既有审批/权限与真实外部结果。不能把平台备货单当销售订单，更不能把1688采购累计进GMV。

### 4.4「我的收益」：回答“赚到了吗？”

首屏四张指标：`确认的销售收入`、`已知成本`、`可归属贡献利润`、`待核对金额`；每张必须标币种、周期、口径、数据刷新时间及来源状态。如果利润仍部分估算就不叫“真实利润”。

异常解释链：利润下降 → 选择 Store/商品 → 看采购价/物流/平台费/退款/广告的已核实及估算部分 → AI 建议 → 审批动作 → 执行结果。未归因费用另列，不进行跨币种裸加；确认到账与销售额不同。

### 4.5「全部工具」：专业能力不是被删除

通过搜索、收藏、近期使用、旧8域分类展示全部授权专业页；仍支持市场洞察、Listing编辑、规则/类目映射、库存、报表、广告、Workflow监控等。Guided 默认隐藏高级工具的导航噪声，工具柜始终可查；已禁用能力显示状态与原因，禁止假按钮和纯展示空壳冒充业务功能。

## 5. 零基础纵向完整旅程 J0（必须先做出可跑通版本）

| 阶段 | 用户自然语言任务 | 当前页面主要字段 | 明确的CTA与行为 | 数据/可信度门禁 | 下一步 |
|---|---|---|---|---|---|
| J0-01 | 告诉系统我的情况 | 市场、预算币种、时间、供应能力、目标 | `生成我的起步路线` 保存 USER_DECLARED | 未知允许；不推断资金/开店资格 | 我的生意 |
| J0-02 | 找一个值得研究的方向 | 市场、类目、体量范围、需求证据、来源时间 | `了解为什么推荐` `加入研究清单` | 供应商销量≠海外需求；数据不足给调查任务 | 机会详情 |
| J0-03 | 找到能卖的货源 | 供应商、报价币种、MOQ、样品、交期、是否支持代发 | `比较货源` `选择候选供应` | 历史报价/库存/代发能力逐项标可信度 | 商品档案 |
| J0-04 | 判断预算能否承受 | 单件采购、运费、平台费、退货、税费、币种、最低价 | `保存试算` `补充缺失费用` | 成本不全不给“盈利保证” | 店铺/市场 |
| J0-05 | 确认怎么开店 | 平台/市场/入驻主体资格/店铺授权状态/平台能力 | `查看官方开店要求` `连接已有店铺` | 无官方能力则提供外部步骤且不冒充开店成功 | 准备上线 |
| J0-06 | 把商品做好 | 规格、合法图片、标题、合规材料、目标店铺 | `补齐当前资料` `检查销售准备` | 素材授权UNKNOWN禁止正式自动提交；检查按目标市场 | Launch |
| J0-07 | 发起上线，知道处理到了哪 | stage、actor、平台回执、缺失材料、可执行动作 | `继续当前步骤` / 等待时无虚假按钮 | SUBMITTED≠ACTIVE；未知原始状态停止自动推进 | 待办或监控 |
| J0-08 | 真的来单了怎么做 | 订单、货源、履约方式、成本、时限 | `处理这笔订单` | 要真实订单事实，无单时仅显示准备内容 | 采购/物流 |
| J0-09 | 第一单赚了多少 | 销售/已结算/退款/归属费用/利润 | `查看收益明细` `记录经验` | 未结算且成本不全显示预估/待核实 | 持续优化 |

**并行处理：**开店资料核实、素材准备、供应询价可在其他步骤等待时进行；后端决定依赖，前端不得硬编码十步严格顺序。所有研究方向允许“保存后退出/换方向/取消而不付款”。

### 5.1 S04「找商品方向」在 R3 中的正确定位

- 它**不是**主侧栏的独立一级页，而是“我的商品 → 我想找商品”的研究步骤。
- 搜索字段首屏只展示：目标市场、预算区间+币种、商品偏好/风险过滤、关键词（可选）；高级展开品类、重量、认证/危险品排除、履约模式、MOQ上限等。
- 结果最多优先展示 3–5 个可说明依据的候选，而非上百个“爆款”；支持比较2–3个方向。
- 机会卡字段：研究方向名、目标市场、需求信号及原始来源、更新时间、竞争信息及有效性、货源候选、潜在成本缺项、合规风险、数据可信度、推荐解释和`值得进一步查什么`。
- 显示四类证据：**VERIFIED_EXTERNAL**（可核实外部）、**OBSERVED_INTERNAL**（Workspace真实经营）、**MODEL_ESTIMATED**（模型判断）、**MISSING/STALE**（缺失/过期）；演示数据另加 `CONTRACT_TEST/DEMO` 显著标签。未达到最低证据门槛不显示“销量增长42%”“机会评分92”这类精确结论。
- CTA：`查看依据`、`加入研究清单`、`寻找货源`（带 opportunity_id/market），`换个方向`；绝不直接触发采购或上架。

## 6. 用户一次操作：必须有稳定“任务契约”

### 6.1 目标 read model（示意，不代表现有API已返回）

```json
{
  "task_id": "source:object:action:version",
  "workspace_id": "server-resolved",
  "source_ref": {"domain": "LAUNCH", "entity_id": "...", "revision": 6},
  "target": {"type": "PRODUCT", "id": "...", "label": "示例商品"},
  "shop_id": "optional",
  "title": "请补充有授权证明的商品图片",
  "reason_code": "ASSET_RIGHTS_UNKNOWN",
  "priority": {"level": "HIGH", "rule_version": "..."},
  "state": "NEEDS_USER",
  "assignee": {"kind": "MEMBERSHIP", "id": "..."},
  "deadline": null,
  "allowed_actions": [{"code": "OPEN_ASSET_REGISTRATION", "label": "去补充素材", "href": "/app/products/.../assets?..."}],
  "evidence": [{"source": "product_asset", "version": 3, "verification": "UNKNOWN"}],
  "data_quality": "PARTIAL",
  "observed_at": "2026-10-14T00:00:00Z",
  "return_to": "/app/products/.../launch/..."
}
```

- **事实源**：Launch、Product、Shop、Order、Finance、审批等原有领域；任务聚合负责 join/filter/dedup/read model，不复制交易数据。
- **任务去重**：一个业务事实允许来自多个来源（Launch、Workbench、Alert），按 `workspace+source business identity+required action/revision` 去重；保留 all sources 与来源版本，防止同一商品缺资料显示三个重复待办。
- **任务状态**：NEEDS_USER、WAITING_EXTERNAL、BLOCKED、IN_PROGRESS、RESOLVED、UNKNOWN。与Workflow生命周期状态/外部平台状态/数据可信度**分层分开**。
- **合法动作**：从后端状态机及权限返回 `allowed_actions`；前端只能显示/请求，不可客户端自己“批准”。403/409/422必须返回可操作错误与恢复方案。
- **候选API**：若已有workbench未提交代码可复用，先排查归属，设计 `GET /api/workbench`（任务摘要）和 `GET /api/tasks`（授权、筛选、分页、可靠来源）等聚合契约；如无此功能，由R0论证最小增量，不凭空声称已有。
- **不强制新增实体表**：无需持久化的自动推导待办可直接派生；确需人工指派、用户确认、到期提醒、审计的任务以现有 Workflow Step/Action/任务实体或最小增量持久化。

### 6.2 前端统一 Feature Data Layer / BFF

```text
真实 API响应（版本化）
   → domain adapter（字段校验+权限范围+数据可信度）
   → stable ViewModel（对象/任务/行动/状态）
   → 业务页面和组件
```

- DTO 以**真实后端 payload**写契约测试，严禁盲猜 `items/data/channels`；动态 data shape mismatch 不能 silent fallback 成空列表。
- 后端聚合层只聚合/派生/排序；价格/利润/权限/合规决策由已有服务负责。
- 数据请求生命周期绑定 Workspace/Store/Query，AbortController或等效取消；迟到请求不能串空间写缓存。
- 读取按首屏需用懒加载；一个模块失败保留其他模块数据，并显示“部分不可用/重试/最近成功更新时间”。

### 6.3 统一跨页返回契约

`intent_id? + product_id? + shop_id? + run_id? + step_code? + return_to?`。

示例：从商品A/Store B Launch Step LABEL → 进入素材登记 → 保存 → 回到 **原 Run/原 Step** → 触发只读刷新 → 由服务端确定下一合法动作。`return_to` 必须站内路径白名单，目标数据再验服务端授权；不得重放旧action或使用旧revision。

## 7. R2 E01–E12：改造清单和可验收断言

| 问题 | 实施措施 | 通过标准（示例） |
|---|---|---|
| **E01 渠道DTO** | `ProductDetail` 的 adapter 消费 `channels`、`shop`、`active_launch`、`history`，建立商品×Store行 | 同商品双店两条独立进度；原 `items` 错读测试能失败 |

| **E07 首页冗余** | 唯一主任务+最多三项待办+补充视图 | 不重复出现同一任务；新手首屏无无意义空BI |
| **E08 功能入口杂乱** | 默认4+1、对象深链接与可搜索工具柜 | 旧业务全部有归宿，日常只暴露有关任务 |
| **E09 channels 路由双声明** | 单一路由manifest，去除占位抢占；保留旧链接兼容 | `router.resolve`、浏览器实际命中正确组件 |
| **E10 权限和模式混乱** | `allowed_actions` + service scope；effectiveMode单一优先级（服务器偏好→用户本地临时预览→默认值，规则需冻结） | READ_ONLY无写动作；模式切换不扩大权限；刷新后偏好一致 |

## 8. 组件与互动规范：从“漂亮”转成“可办事”

### 8.1 共享组件（优先复用改造，不再堆新同义组件）

| 组件 | 必须实现的行为 | 复用范围 |
|---|---|---|
| `AppShell` | Workspace/店铺范围、用户模式、4+1导航、全局搜索与任务入口 | 所有商户页 |

| `NextActionPanel` | 来自服务端 allowed_actions、不可执行原因、结果与回退 | 商品、订单、Launch |
| `DataProvenance` | VERIFIED/OBSERVED/ESTIMATED/MISSING/DEMO、更新、来源 | 选品、成本、财务、合规 |
| `MoneyValue` | 币种、估算、时点、口径、缺失 | 成本、定价、收益 |

### 8.2 四个必须分离的状态轴

1. 页面载入：LOADING / READY / PARTIAL / ERROR / FORBIDDEN。
2. 业务任务：NEEDS_USER / WAITING_EXTERNAL / BLOCKED / RESOLVED 等。
3. 平台事实：SUBMITTED / REVIEWING / ACTIVE / PAUSED / UNKNOWN（需平台证据）。
4. 资料来源与可信度：OBSERVED / VERIFIED / ESTIMATED / MISSING / STALE / DEMO。

不要拿一个`green/orange/red`共享字典混合全部业务事实。状态同时有可读文案、图标和文本说明，不只靠颜色。

### 8.3 操作失败的恢复

- 401：登录过期并保留非敏感草稿。
- 403：解释无操作权限并提供联系管理员入口，不显示“没有记录”。
- 409：版本冲突提示已变更字段、拉取最新状态且保留用户输入；禁止重放旧审批。
- 422：字段内联校验及引导，不直接扔JSON。
- Timeout/断线：显示“结果待核查”，先按外部ID或幂等键读取确认再重试，尤其发布/采购/价格动作。
- 部分数据源失败：保留其他可信区块，标记更新时间和缺失源。
- 未实现/不可用：禁用或移出默认流并解释原因；不得用 “提交成功”Toast 冒充事实。

### 8.4 视觉规范（可落地，而不是只谈“高级感”）

- 默认正文14–16px；桌面左导航紧凑、主工作区宽度适中，不盲目三栏；主任务全宽，其余按需。
- 主操作每个操作区1个明确CTA；高级编辑分层，但专业列表每行允许操作。
- 行业语言翻译：Listing→销售内容，Launch→准备上架/上线进度，Compliance→销售合规，Workflow→自动处理记录；专业视图保留英文术语。
- 图表仅在真实可比较数据存在时显示；无业务数据时显示下一步任务而非0线图。
- 桌面1440×900、1366×768主流程；平板768、手机390基本待办及审批可用；复杂批量表可合理横滚。
- 组件键盘焦点、表单标签、错误定位和风险确认可访问。

## 9. Agent OS 在页面上的使用原则

- **主观判断与任务事实分离。** “合规缺材料”来自规则服务；AI只解释什么材料、为什么需要、如何准备。
- **上下文只给必要信息。** Orchestrator拿Workspace、当前目标对象、用户授权和对应证据摘要；领域Agent按需检索，不每次灌入全仓历史。
- **建议结构化。** `insight`、`evidence_refs`、`uncertainties`、`risk_level`、`suggested_action_code`、`approval_required`、`outcome_ref`。
- **可解释的未解决。** 无法验证市场需求、供应报价、店铺资格或合规时，AI要说“缺什么”，不瞎编。
- **动作走原系统。** Permission → Scope → Policy → Risk → Approval → Executor → Business Service → Workflow事实推进；前端按钮不直接更改数据库。
- **个性化按事实来源。** Capability Profile USER_DECLARED / SYSTEM_OBSERVED / MODEL_ESTIMATED；Business Stage deterministic and versioned；Guided/Professional只调信息密度。

## 11. 开发执行计划：设计一次冻结，按可用旅程分批实现

### Phase R3-0｜现场基线与安全护栏（必须第一步）

- 检查 `git status`、未提交workbench/action_queue/旧Dashboard/入口配置归属、当前 HEAD、运行产物、Python/Docker部署；未经授权不得reset/混交/覆盖。
- 建立 **真实页面与后端能力矩阵**：有实现且连通 / 错接 / 仅演示 / 无接口 / 未核实。复现E01–E12并用请求response保存脱敏样本。
- 路由解析单表、权限目录、Workspace/Factory身份、当前 V9 build与正式入口差异。
- 设计R3唯一信息架构和四个工作区骨架，建立路由/字段/状态/返回/任务契约；冻结后除故障修复不逐页推翻。
- **退出条件**：一份真实页面矩阵，一份E01–E12复现证据与修复策略，一份R3 UI契约与风格基线；无业务代码破坏。

### Phase R3-1｜契约修复+AppShell（双轨交付）

- 修E01–E06、E09、E10等已确认断点；按Scope与决策权限服务端复核。
- 新 4+1导航/工具柜/统一ContextHeader/页面与数据状态；旧路由兼容；工作区切换缓存/请求处理。
- **退出条件**：双店商品渠道准确、素材登记/核验按真实契约操作；新旧链接不丢；至少一条真实浏览器对象导航链路。

### Phase R3-2｜零基础 J0 纵向主链（用户一眼能用）

- 起步条件收集 → 我的生意 → 找方向 → 对比货源 → 商品卡片 → 成本可信试算 → 店铺资格/连接 → 销售准备 → Launch等待与人工任务。

- **退出条件**：真实浏览器新手不依赖旧8域菜单能完成全部本地可控准备步骤；所有上下文与返回不丢失。

### Phase R3-3｜有商品/有店铺分支与 J1/J2

- 自有SKU导入 → 市场匹配 → 上线；已有Store授权 → 同步业务诊断；商品多店/待办聚合 → Launch → 素材/核验 → 回原步骤 → Action结果。
- Workbench WIP代码首先保护，再决定集成；杜绝两个任务聚合真相。
- **退出条件**：双店独立、跨角色权限、审批有效、人工证据闭环、事件/刷新可追溯。

### Phase R3-4｜订单与收益完整闭环 J3/J4

- 销售订单→货源/采购/履约/退款→已发生费用→结算归因→真实利润与AI建议回执。
- 缺真实订单/结算平台能力则严谨显示限制；可用隔离Contract E2E验证内部流转。
- **退出条件**：从异常订单/利润出发≤2次导航到处理位置并返回；不串财务口径。

### Phase R3-5｜专业用户、Factory、Console 与工具柜收口

- 批量上架多店、保存筛选、专业监控页/渠道规则；工厂/合规/平台身份投影独立；把所有旧业务页面按页面矩阵迁移/合并/兼容。
- **退出条件**：旧业务功能100%有归宿，未接能力清晰标注；专业角色更高效而非被简化逻辑削弱。

### Phase R3-6｜真实用户验收、性能、发布切换

- 逐页实际浏览器走查、组件/契约/权限/E2E、复杂/空/错误/多店数据；用户不提示完成核心任务。
- 确认构建SHA、路由深链、Docker、回退、后端增量契约兼容；逐步灰度，旧版切换方案保留到观察完成。
- **退出条件**：见12章全部红线与关键KPI，绝不以文件数和Vitest数量代替用户体验。

## 12. 本轮验收：不是“页面数量”，而是“经营任务真的能做”

### 12.1 试点可用性标准（作为候选门槛，R3-0测基线确认）

| 指标 | 建议门槛 | 证据 |
|---|---|---|
| 新手入口可理解 | 未参与实现的至少3人，30秒内找到首次经营主任务 | 屏幕录制+点击路径+口头复述 |
| 本地可控 J0/J1/J2 | 首批任务不经口头指导完成率目标 ≥90%，外部平台等待算“正确等待” | 测试账号+任务路径+DB/API断言 |
| 少绕路 | 从工作台到目标处理 ≤2次导航；从商品/订单回原任务无需重选 | URL/点击记录 |
| 诚实可信 | 核心路径0处将错误→空、未知→0、提交→在售、估算→真实、建议→已执行 | 负例API/浏览器证据 |
| 能处理异常 | 401/403/409/422/超时/权限撤销/重复提交均能恢复或明确阻断 | UI视频+Network+事件审计 |
| 角色隔离 | OWNER/OPERATOR/READ_ONLY/COMPLIANCE/FACTORY/PLATFORM全部校验 | 后端权限断言+浏览器角色测试 |
| 回归覆盖 | 旧功能逐项落实迁移/合并/兼容；无静默功能丢失 | 页面矩阵完成率100% |
| 视口与可访问性 | 1440×900、1366×768桌面；768/390阅读与简单操作；键盘与错误聚焦可用 | 实际截图+操作录屏 |
| 性能 | 同设备同数据度量，受控场景主内容目标≤2s，长列表分页/虚拟化 | DevTools/Lighthouse或等效记录 |
| 正式切换 | 构建版本/静态资源/入口一致，回退不撤销业务事实 | build-info+切流/回退演练 |

小样本可用性测试不构成统计显著证明，只用来识别重大认知与交互障碍。外部API未真实联调时只能宣称内部闭环/模拟契约测试通过。

### 12.2 必测旅程矩阵

- 新用户无货源无店铺→找到方向→比较报价→成本部分估算→要求开店资料；未知市场条件不误导。
- 自有工厂SKU→海外需求核对→商品准备→选择店铺→Launch；Factory Partner只看自己相关任务。
- 已有店铺用户→进入实际在售商品→利润异常→建议审批→查看结果。
- 商品双店独立Launch、旧 published不能冒充ACTIVE、审核回执未知阻断。
- 素材注册必要字段、权益状态UNKNOWN阻断、核验角色不得自审、409版本冲突保留输入。
- 商品缺货→备货/采购→真实订单履约→退款及财务归属；1688不进入GMV。
- Workspace切换过程中迟到响应不可串数据；跨店/跨身份API服务端拒绝。
- 业务API500时显示部分数据失败而非空；断网提交进入待核查而非盲重试。
- 错误链接/旧链接/深路由刷新/正式构建回退均通过。
