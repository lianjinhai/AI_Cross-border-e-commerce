# 角色界面差异化设计方案（待论证）

> 触发：用户提问「对应的角色界面有没有重新设计好的？」
> 诚实结论：**没有**。目前只做了**权限裁剪**（隐藏按钮、过滤菜单），未做**角色界面设计**（专属工作台、角色化信息架构）。

---

### 1.1 已完成的（权限层）

|---|---|---|---|

### 1.2 未完成的（界面层）——这是用户问的"重新设计"

| 角色 | 现状 | 应有（理想） | 差距 |
|---|---|---|---|
| **COMPLIANCE** | 复用业务页面（商品池/Listing/合规/BI），按钮被裁剪 | **合规工作台**：待审批队列、风险商品排行、规则版本状态、批量审批 | 完全缺失 |
| **READ_ONLY** | 复用业务页面，按钮消失 | **只读模式明确提示**（顶部横幅"当前为只读账号"）+ 隐藏写操作列 | 缺失（用户困惑） |

## 二、方案设计

### 2.1 合规员专属工作台（优先级 P0）

**为什么最需要**：合规员的职责是"审批 + 检测"，但当前打开系统看到的是商品池/订单等无关信息，**待审批的 Listing 藏在 Listing 页的表格里**，需要逐行找。

**方案：新增 `/compliance-workbench` 页面**（合规员默认落地页）

| 区块 | 内容 | 数据来源 |
|---|---|---|
| **待我审批** | Listing 复核队列（manual_required 状态），支持批量审批/驳回 | `GET /api/listings?status=manual_required`（需确认端点） |
| **风险商品 Top** | 合规分最低的商品（高风险优先） | `GET /api/compliance/reports?risk_level=high` |
| **规则版本状态** | 各平台规则包版本 + 更新时间（合规员需关注政策变化） | `GET /api/shops/platform_rules` |
| **一键检测** | 选商品/Listing 发起检测（compliance:check 权限） | `POST /api/compliance/check` |

**菜单调整**：合规员菜单从 4 页白名单改为「合规工作台 + 合规检测 + Listing 工作台 + BI」——**工作台放首位**。

### 2.2 只读模式明确提示（优先级 P0）

**为什么需要**：只读账号看到的是"缺了一半功能的界面"，用户不知道是权限问题还是系统故障。

**方案**：
1. Layout 顶部显示常驻横幅（仅 READ_ONLY）：`当前为只读账号，写操作已隐藏；如需编辑请联系管理员`
2. 表格的「操作」列在只读时隐藏（而非显示空列）
3. 路由守卫已做（越界跳转），无需改

### 2.3 运营/管理员视角微调（P2，可选）

| 项 | 说明 |
|---|---|
| OPERATOR 隐藏 `/settings` `/users` | ✅ 已做 |
| OWNER 显示全部 | ✅ 已做 |

**不做**：运营与管理员共用业务界面是合理的（职责重叠度高），无需强行分化。

### 2.4 工厂门户（已独立，P3）

已有独立页面与菜单，**保持现状**（前端按钮权限已补 `supply:write`）。

## 三、多视角论证

### 3.1 产品视角

**质疑 1**：合规员工作台是否值得单独开发？
**分析**：合规员的日常是"批量审批 + 监控风险"，当前需在 Listing 表格中逐行找 `manual_required`。**这是真实效率损失**（一个中型卖家每天可能有数十条待审批）。
**结论**：值得。且实现成本可控（复用现有端点 + 一个新页面）。

**质疑 2**：只读提示是否过度设计？
**分析**：不是。用户明确反馈"角色界面没设计好"——只读账号看到残缺界面却无解释，是**体验缺陷**。
**结论**：横幅 + 隐藏空操作列，成本极低（< 20 行代码）。

### 3.2 工程视角

**质疑 3**：新增页面会不会与现有页面重复？
**分析**：合规工作台是**聚合视图**（把散落在 Listing/合规/规则三处的信息集中），不是复制。它复用现有端点，不新增后端。
**结论**：无重复。但需确认 `manual_required` 的查询端点是否存在（**实施前必须核实**）。

**质疑 4**：只读提示的实现位置？
**分析**：Layout 是唯一入口（所有页面都经过），放这里最合适；`roleKey() === 'READ_ONLY'` 判断。
**结论**：单点实现，不散落。

### 3.3 安全视角

**质疑 5**：界面差异化会不会削弱权限边界？
**分析**：不会。界面差异化是**体验层**，后端 `require_*` 是安全层，两者独立。新增工作台页面仍需路由守卫保护（合规员可进，其他角色按规则）。
**结论**：需在工作台路由上加 `meta` 标记并扩展守卫规则（**实施要点**）。

**质疑 6**：只读账号隐藏操作列会不会让管理员也看不到？
**分析**：不会，条件是 `roleKey() === 'READ_ONLY'`，其他角色不受影响。
**结论**：安全。

### 5.3 实施前核实发现的缺口（2 个，已补）

方案要求"实施前必须核实端点"，核实后发现：
1. **`manual_required` 无法查询**：它是复核决策的返回值，但 Listing 列表只支持 `status`（draft/published）→ 新增 `/listings/review-queue`
2. **合规报告无法按风险等级过滤** → 新增 `risk_level` 参数

**这印证了"先核实再实施"的价值**——否则会写出依赖不存在端点的页面。
