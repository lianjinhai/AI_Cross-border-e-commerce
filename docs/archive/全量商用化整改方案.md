# AI 跨境电商 ERP 全量商用化整改方案

版本：2026-09-22 v1.0  
原则：安全与数据正确性优先；协议实现不等于生产验收；没有真实证据不得标记“商用可用”。

## 一、目标与完成定义

项目最终需要同时满足以下条件：

1. 多租户、认证、OAuth、平台凭证不存在已知高危缺陷。
2. 1688 作为货源，销售平台作为市场，平台角色不可混用。
3. 每次上架都经过规则同步、合规复核及可审计审批；明确违规不可人工覆盖。
4. TikTok、eBay、Walmart、Lazada、Shopee 均完成契约沙箱；真实能力继续标注“待实店验收”。
5. Agent 工作流可恢复、可重试、可暂停，业务阻断不能被误报为成功。
6. 订单、费用、币种、退款、采购、广告和结算口径可对账。
7. 预测使用真实历史数据完成时间切分回测；未过门槛禁止自动采购。
8. 后端测试、前端构建、端到端验收、安全审计、数据库迁移和恢复演练全部通过。

## 二、执行阶段与顺序

### 阶段 A：P0 安全与数据隔离

- 修复用户管理跨租户读取、修改、删除。
- 密码改为用户级随机盐并兼容升级旧散列。
- 生产环境拒绝默认 JWT 密钥和默认管理员密码。
- 增加登录限流、账号状态和 Token 版本撤销能力。
- OAuth 增加一次性 state、过期、消费记录和回调绑定；为支持的平台预留 PKCE。
- 平台密钥与 Token 应用层加密存储、轮换和脱敏审计。
- CORS 改为环境白名单。

验收：跨租户攻击测试、OAuth CSRF/重放测试、密钥不落明文测试全部通过。

### 阶段 B：数据库约束与正式迁移

- 引入 Alembic；保留 SQLite 开发兼容，生产推荐 PostgreSQL。
- 为订单、SKU、类目映射、工作流模板、发布尝试、采购/退款/结算单号增加租户级唯一约束。
- 财务金额迁移为 Numeric/Decimal；状态增加约束；明确删除策略。
- 订单粒度扩展为订单头、订单行、费用、退款和平台结算。

验收：旧库迁移、回滚、重复数据预检及约束测试通过。

### 阶段 C：上架复核与实时规则治理

- 建立提交、复核、人工审批、驳回、修改后重提的状态机。
- 审批使用独立 compliance_approver 权限；提交人不能审批本人内容。
- 前端增加待审批队列、规则证据、版本、内容差异和审批意见。
- 规则包增加 Schema、签名、版本防降级、站点/国家/类目/资质维度、变更影响分析和告警。
- eBay、Walmart、Lazada 补齐自动规则包；不可自动判断项强制人工审批。

验收：任何发布入口均不可绕过复核；规则过期或同步失败默认关闭放行。

### 阶段 D：平台发布与订单全链路

- TikTok：图片上传、Global Product、商品发布与最终状态。
- eBay：Inventory Item → Offer → Publish Offer → 反查确认。
- Walmart：OAuth、订单、Feed 提交、Feed/商品级轮询、部分失败恢复。
- Lazada：授权、订单、商品创建、站点类目 Schema 和错误恢复。
- Shopee：真实店铺授权、类目映射、图片、发布和拉单最终验收。
- 全平台覆盖多页遍历、限流、Token 失效、超时、部分成功、幂等与重放测试。

验收：本地契约沙箱全通过；官方 Sandbox/Development Shop 单独留存验收证据。未拿到账号时不得宣称完成生产验收。

### 阶段 E：生产级 Agent 协同

- 进程内线程升级为持久化任务和数据库租约。
- 增加步骤重试、超时、心跳、暂停、取消、恢复、补偿和死信。
- 固化 Agent 输入输出 Schema、工作流版本和决策证据。
- 区分技术成功、业务成功、部分成功和人工等待。
- 上架复核阻断时，后续发布与广告步骤跳过，工作流标记 blocked/partial，而不是 success。

验收：服务重启、重复派发、Worker 崩溃和并发执行测试通过。

### 阶段 F：商用数据分析与预测

- 统一 GMV、净收入、贡献利润、ROAS/ROI、退款率的币种和会计期间。
- 引入汇率版本、平台费、支付费、税费、物流、仓储、退款和广告归因窗口。
- 数据质量增加断档、漂移、对账、血缘和修复任务。
- 预测真正使用价格、促销、断货、节假日、平台、国家等特征。
- 对 last-value、移动平均、Croston/TSB、季节模型进行同窗回测和自动选择。
- 保留模型版本、训练截止、预测快照、WAPE、Bias、覆盖率和基线提升。
- 商用门槛成为可执行门禁；真实历史订单不足或回测不通过时禁止自动采购。

验收：真实订单的时间切分回测报告通过既定阈值，且业务方签字确认后才能标记 commercial_ready。

### 阶段 G：前端、运维与发布

- 补齐审批台、平台验收台、工作流恢复台、数据可信度与预测监控。
- 配置 PostgreSQL、任务 Worker、TLS、日志、指标、告警、追踪、备份与恢复。
- 修复验收脚本，使其可自动启动隔离环境并输出机器可读报告。
- CI 强制执行单元、契约、迁移、安全、端到端和前端构建。
- 同步 README、CONTRACT、能力矩阵和平台验收状态。

验收：一键部署、一键验收、备份恢复演练、灰度与回滚流程全部完成。

## 三、能力状态定义

- `planned`：只有调研结论。
- `protocol_ready_unverified`：协议与本地契约已实现，尚未通过官方环境。
- `sandbox_verified`：通过官方 Sandbox/Development Shop。
- `production_pilot`：真实店小流量试运行并可回滚。
- `production_verified`：真实订单、发布和异常恢复均留有验收证据。

状态只能逐级晋升，必须记录验收时间、账号环境、规则版本、请求追踪 ID、结果和审批人。

## 四、全局质量门槛

- P0/P1 安全问题为零。
- 后端测试、前端构建、契约沙箱和端到端测试全部通过。
- 核心流程具备失败注入测试，且服务重启后可恢复。
- 所有自动业务决策都有来源、版本、证据、操作者和回滚路径。
- 演示数据、导入数据、平台 API 数据严格区分，BI 默认不混入演示数据。
- 未完成真实账号验收的能力始终显示“协议实现、待实店验收”。

## 五、当前执行批次

本批次按以下顺序实施：A（安全）→ B（关键唯一约束）→ C（审批闭环）→ E（工作流状态语义）→ F（预测门禁）→ G（验收和文档）。平台官方账号验收因外部审批等待，先完成本地契约与证据结构，不伪造验收结果。
