# 项目开发总结与交接快照

> 日期：2026-10-14｜状态：静态核对完成；本次未运行业务回归、数据库迁移或外部平台联调。
> 项目：AI 跨境电商经营平台。代码基点：HEAD `dac556a`，另有未提交工作区增量。
> 配套：[详细策划书](../PROJECT_MASTER_PLAN.md)、[前端整改 R2](../UI_REFACTOR_BLUEPRINT.md)。本文件为日期快照，不代替各域持续更新的进度事实源。

## 1. 总体判断

项目已从商品采集、Listing 发布和传统 ERP 功能组合，发展出 Workspace 权限基础、受控 AI Action、平台生命周期框架和 V9 前端。已有可复用代码资产较多，下一阶段的重点是完成领域业务链路和前端承接，不能重新建一套 ERP。

目前不能认定“全平台真实接通”“复杂商品生命周期全部跑通”“Agent OS 全部迁移完成”或“V9 用户体验终验完成”。依据分别是：适配器状态仍含未核验/受限；Launch 领域事实和动作仍存在缺口；Agent 迁移台账未收口；用户明确反馈旧版和 V9 均不好用，静态核对发现实际契约错接。

不提供总体完成百分比：各模块成熟度、验证层级、真实平台授权和当前部署状态不同，无法用一个百分比准确表达。

## 3. 已形成的主要成果

### 3.1 业务底座与经营模块

已有商品采集/标准化/评分、供给报价、供应商与工厂、采购收货、库存、Listing、合规检测、订单、售后退款、账期结算、成本和经营分析等模块。

模型入口 `backend/app/models.py` 可见 Product、Listing、Shop、PurchaseOrder、Order/OrderLine/OrderFee、ComplianceReport、ProductComplianceEvidence、Warehouse、InventorySnapshot 等对象；对应路由及服务已存在。这是复用基础，不代表所有模块的当前分支已独立复测。

物流、退款、广告等功能须区分本地记录与外部执行。不能根据“发货”“退款”“预算”按钮推断已经对接物流商、支付渠道或广告平台真实账户。

### 3.2 Workspace 与权限

已建立 Workspace Context、角色和成员边界、平台/工厂/商家分流、可信身份传递、Store Scope 与发布撤权重验等基础。前端路由呈现不能作为安全依据，后端仍是权限边界。

`docs/WORKSPACE_MIGRATION_PROGRESS.md` 存在早期主库快照，例如 owner 字段和范围数据的历史遗留；这些记录不能直接当作当前主库状态。本轮没有读取主库，后续若要处置，应先按只读预检重新核实。

### 3.3 发布与平台状态

已推进店铺级发布意图、回执、派生草稿、审批指纹和执行检查。提交回执与真实在售核验分开；原始 ACTIVE 文本不能直接成为 VERIFIED。

Store 上下文包含市场和经营方式，发布检查不再随意从商品或平台默认国家推断。素材权利事实进入发布条件，授权撤销、版本变更、失效会影响准入和审批依据。

### 3.4 Platform Workflow / Launch

| 能力 | 已有实现/证据 | 仍需注意 |
|---|---|---|

`backend/app/workflows/launch_facts.py` 仍明确指出 PriceReview/StockPreparation 等领域事实未接入。`backend/app/routers/launch.py` 的 sync 仅允许 refresh，调用内部事实刷新；不能称为完整 webhook/polling 外部状态同步。

### 3.5 素材治理

ProductAsset 及迁移已提交；支持版本追加、来源、权利状态、适用市场/平台、有效期、人工登记和独立核验。已有查询、登记、核验 API，发布侧有权利检查。

边界：主要管理 URI/摘要与证据，不等同上传托管和远端实际文件真实性核查。旧图片不会自动获得版权。OWNED 与授权/许可材料按各自规则判断，不把所有用户素材强制升级为双人审批。

V9 当前调用与字段存在错接，不能因后端服务存在就把素材中心判为已交付可用。

### 3.6 Agent OS

冻结的八类领域 Agent 契约、Tools、受控 Action 和部分可信产物保存已推进。架构文档 §18.3.1 记录读取迁移完成、写路径迁移进行中，后续 Runtime/会话与完整追踪步骤未完成。

当前 `backend/app/agents/base.py` 仍自行创建 SessionLocal；文档记录 Orchestrator 仍有同步直调路径。已有 trace_id 使用不等于完整 Task Graph、父子追踪和统一 Runtime 已完成。

待迁移范围包括客服/知识学习、部分缓存、告警和基础审计等，具体按架构台账与当前代码逐项核验。不得将冻结架构图作为已建系统的全部实现图。

### 3.7 V9 前端

已有三空间外壳、域导航、API 模块、共享组件、主要业务页面及蓝图 R1 增量。Git 记录可追溯 UX-B/C/D/E、路由合并、历史验收和 R1 补齐。

用户在 2026-10-14 明确反馈 8000 与 8001 均混乱，因此当前业务可用性仍未满足用户预期。R2 蓝图已据此提出以 V9 为主基底的整改，不再新增第三套前端。

### 3.8 工程与部署

仓库有 Alembic 迁移、测试、Ruff、文档门禁、隔离 E2E、备份恢复、Docker/Compose 等资产。迁移文件链已包含素材增量；本轮未检查主库执行到了哪一版。

当前 Dockerfile 仍从 frontend 构建并复制旧产物；已读 CI 的前端和基线 job 也使用旧目录。工作区新增可配置前端产物位置及 build-info 的变更尚未提交。V9 的生产构建、CI 和正式入口一致性应作为待收口工作。

## 10. 经验与下一阶段管理建议

### 应保留的做法

- 复用实体和服务，避免第二套 ERP。
- 将店铺范围、版本、幂等和撤权检查放在后端。
- 将提交、审核、在售与核验分开表达。
- 明确测试/演示与真实数据，未接通动作保持阻断。
- 隔离库测试和迁移保护，不让验证污染主库。

### 需要改变的做法

- 不再按“新增页面数量”描述主要进度，改为“用户完成了哪条业务路径”。
- 不再仅凭组件纯函数测试判定界面可用，补充真实请求、表单和浏览器交互。
- 不在尚未接通后端时先铺满可点击菜单，再把占位当完整产品。
- 不用总体“完成”覆盖局部未验证，记录提交版本和能力边界。
- 不复制旧结论排期，先看当前源码和最新阶段记录。

下一阶段按 `docs/PROJECT_MASTER_PLAN.md` 的 M0—M5 管理，前端细节按 `docs/UI_REFACTOR_BLUEPRINT.md` 的 R0—R5执行。先做清晰可用的商品上线与待办处理，再扩展经营链路。
